# Story 16.2: Select an Active Theme

Status: ready-for-dev

## Story

As a user,
I want to choose which installed theme is active for my view,
so that I see the branding my organization has configured, or the default if none is selected.

### Persona journey stub

**Priya-member (any authenticated org member, no special role required):**
1. Priya's OrgAdmin installed a custom theme (`acme-brand`) via Story 16.1 and called the reload endpoint. Priya has not touched anything yet — she still sees the base theme, because 16.1 only *installs* themes, it never changes what anyone sees (confirmed in 16.1's own Out of Scope section).
2. Priya opens `(app)/settings/themes/`. She sees a list: "Default" (base theme, currently selected) and "acme-brand" (available, since it loaded successfully).
3. Priya selects "acme-brand" and the page saves immediately (no separate Save button, matching this codebase's other single-field settings pages e.g. `(app)/settings/language/`) — the UI re-renders with `acme-brand`'s colors/radii/fonts applied everywhere in the app, no page reload, no rebuild, no restart.
4. Priya closes her laptop. The next day her org's Owner removes `acme-brand.json` from `VAULT_THEMES_DIR` (maybe it was a trial) and calls `POST /api/v1/admin/themes/reload`. When Priya next loads any page, she sees the base theme (never a broken/unstyled page) plus a one-time dismissible banner: "Your selected theme is no longer available — showing the default." She dismisses it and it never reappears for that same "orphaning" event.
5. This is a **personal, per-user preference** — a colleague of Priya's in the same org can independently select a different theme (or none) without affecting what Priya sees, and vice versa. There is no "org default theme" concept in this story (see Dev Notes "Scope judgment call: per-user vs. per-org").

## Acceptance Criteria

> Every AC below includes both a concrete happy-path example and at least one concrete edge/failure-case example, per this story's authoring mandate. Given/When/Then text for AC-1/AC-2/AC-3 is verbatim from `epics.md` §Epic 16 (lines 2741-2759, Story 16.2's exact text — quoted in Dev Notes/References); everything else (AC-4 through AC-10) is added for this story's completeness, each explicitly flagged as such in its own heading.

### AC-1: users see all currently available themes

**Given** the base theme and any successfully installed custom themes,
**when** a user opens theme selection,
**then** they see all currently available themes to choose from.

- **Happy path example:** `GET /api/v1/themes` returns `200 { "themes": [{ "name": "base", "label": "Default" }, { "name": "acme-brand", "label": "acme-brand" }], "selected": "base" }` — reflecting Story 16.1's `getCompiledThemes()` in-memory list (the same data 16.1's `service.ts` already produces; this story adds a read-only endpoint over it plus the persisted per-user selection) at `apps/web/src/routes/(app)/settings/themes/+page.svelte`, rendered as a radio-button list with "Default" always shown first and pinned even if a custom theme's `name` alphabetically precedes it.
- **Edge case — zero custom themes installed (fresh instance, or `VAULT_THEMES_DIR` unset):** `GET /api/v1/themes` returns `{ "themes": [{ "name": "base", "label": "Default" }], "selected": "base" }` — the page renders with a single, disabled-looking "Default (only option)" entry, not an empty state or an error. This is the common case for every self-hosted install that hasn't run 16.1's install flow yet.
- **Edge case — a theme that failed 16.1's validation on the last reload is never listed:** `VAULT_THEMES_DIR` has `good-theme.json` (loaded) and `broken.yaml` (failed per 16.1's `{ loaded, failed }` reload response). `GET /api/v1/themes` only ever reflects the `loaded` set — `broken` never appears as a selectable option, since it was never compiled. No new logic needed here beyond reading 16.1's existing in-memory compiled-themes list; this AC exists to make explicit that this story does not re-validate or re-surface reload failures, it only lists what's already successfully compiled.

### AC-2: selecting a theme applies it immediately, no rebuild/restart

**Given** a user selects a theme,
**when** the selection is saved,
**then** the UI immediately applies the `[data-theme="name"]` CSS custom-property overrides — no rebuild, no restart.

- **Happy path example:** Priya clicks "acme-brand" in the radio list. The page calls `PATCH /api/v1/themes/selection { "themeName": "acme-brand" }`, which returns `200 { "themeName": "acme-brand" }` and writes the selection to `users.selected_theme_name`. The client-side `apps/web/src/lib/theme/apply-theme.ts` helper (this story's new deliverable — 16.1 explicitly deferred it) sets `document.documentElement.dataset.theme = 'acme-brand'` immediately on receiving the success response — every element styled via the `[data-theme="acme-brand"]` CSS custom-property block (compiled by 16.1) re-renders with the new values with no navigation, no full-page reload, no server restart.
- **Edge case — selecting "Default" (explicitly clearing a custom theme):** Priya had `acme-brand` selected and clicks "Default". `PATCH /api/v1/themes/selection { "themeName": null }` clears `users.selected_theme_name` back to `NULL`, and the client removes the `data-theme` attribute entirely (falling back to the base theme's un-namespaced CSS custom properties, which are always present in the base stylesheet — never toggles to a `data-theme="base"` block, since 16.1 never compiles a `[data-theme="base"]` block for the base theme itself, it's just the app's default CSS).
- **Edge case — selecting a theme name that does not currently exist in the compiled set:** A malicious or stale client sends `PATCH /api/v1/themes/selection { "themeName": "does-not-exist" }` (e.g. a theme that was removed between page load and submit, or a hand-crafted request). The server validates `themeName` against the *current* compiled-themes list (re-read at request time, not trusted from the client's stale page state) and returns `400 { "error": "VALIDATION_ERROR", "message": "unknown theme 'does-not-exist'" }` — the selection is **not** persisted. Write a test asserting the DB row is unchanged after this rejected request (no partial write).
- **Edge case — request body schema hardening (found via Security Audit Personas elicitation):** The Zod schema for `PATCH /api/v1/themes/selection`'s body must bound `themeName` to `z.string().max(100).nullable()` (or the exact max length 16.1's theme-`name` field itself enforces, if one exists — check `theming/service.ts`'s schema validation for the install-time `name` field and reuse the same bound) *before* the compiled-themes-list lookup, not rely on the list-membership check alone to reject oversized/garbage input — this keeps a malformed request cheap to reject (schema validation is O(1), the list-membership check is O(n) over installed themes) and keeps request-body validation errors consistently shaped with every other endpoint's Zod-driven `VALIDATION_ERROR` response. A hacker-persona review of this endpoint found no exploitable path beyond this: `themeName` never reaches storage unless it's already a member of the live, server-validated compiled-themes list (itself already CSS-injection-hardened by 16.1's AC-4), so there is no secondary injection surface here to defend against — this endpoint inherits 16.1's hardening for free rather than needing its own.
- **Edge case — rapid double-submit (double-click):** Priya double-clicks "acme-brand" before the first request resolves. Both `PATCH` calls are independently valid (idempotent — same `themeName`, same end state), so this is not a special case to guard against: the second write simply repeats the first. No optimistic-locking/version column is needed since there's no meaningful "conflict" between two writes of the same or even different desired values by the *same* user — last-write-wins is correct and sufficient here (see Dev Notes "Concurrent access").
- **Edge case — pessimistic UI update, not optimistic (found via Failure Mode Analysis elicitation):** The client must apply `data-theme` only *after* the `PATCH` response resolves `200`, never optimistically on click before the server confirms — if the request fails (network error, `400` unknown-theme, `503` audit-write failure), the UI must remain on the previously-applied theme, not flash to the new one and then revert. Write a component test asserting a rejected `PATCH` leaves `document.documentElement.dataset.theme` unchanged and surfaces an inline error near the radio list (not a silent no-op).
- **Edge case — no FOUC (flash of unapplied theme) on initial page load (found via Failure Mode Analysis elicitation):** `apply-theme.ts`'s responsibility is *live* updates after a selection change within an already-loaded page — the *initial* correct theme on a fresh page load must be set server-side (SSR), by having `(app)/+layout.server.ts` return `appliedTheme` and the root layout template render `data-theme="{appliedTheme}"` directly into the initial HTML (e.g. on the `<html>` or top-level app-shell element), not left for client JS to apply after hydration/mount. Relying on client-side-only application would cause every page load to flash the base theme for a moment before JS runs and corrects it — write a test (or explicit manual verification step, since SSR-vs-CSR flash isn't always unit-testable) confirming the server-rendered HTML already contains the correct `data-theme` attribute before any client JS executes.

### AC-3: orphaned-theme fallback with a one-time dismissible notice

**Given** a user has a custom theme selected,
**when** an admin removes that theme's file from `VAULT_THEMES_DIR` and reloads,
**then** the user's next page load falls back to the base theme silently, plus a one-time, dismissible in-app notice ("your selected theme is no longer available, showing the default") — never a broken or unstyled UI, never a hard error blocking product access.

- **Happy path example:** Priya has `users.selected_theme_name = 'acme-brand'`. An OrgAdmin deletes `acme-brand.json` and calls `POST /api/v1/admin/themes/reload` (16.1's endpoint) — `acme-brand` drops out of the compiled-themes list. Priya's next navigation triggers `(app)/+layout.server.ts`'s load function, which re-checks her stored `selected_theme_name` against the *current* compiled list, finds it missing, and returns `{ appliedTheme: null, orphanedNotice: true, orphanedThemeName: 'acme-brand' }` to the layout. The layout renders the base theme (no `data-theme` attribute set) and shows a dismissible banner once. **Concrete dismissal-key design (concretized via Pre-mortem Analysis elicitation — the original draft only said "scoped to that specific orphaning event" without saying how):** the client stores `sessionStorage['dismissedOrphanedTheme'] = 'acme-brand'` on dismissal; the layout only shows the banner when `orphanedThemeName !== sessionStorage['dismissedOrphanedTheme']`. This means: dismissing it hides it for the rest of that browser session for *that specific theme name*; it does not reappear on subsequent navigations within the same session (same name, matches the dismissed key); but if a *different* theme later becomes orphaned (e.g. Priya switches to a second custom theme which is later also removed), the new orphaned name won't match the old dismissed key and the notice correctly reappears. It does not persist across devices/browsers or past session end (this is a transient UX notice, not a durable audit-worthy record) — a fresh session with the same still-orphaned theme will show the notice again once, which is an acceptable, documented trade-off (favoring "never silently hide a real state change" over "never repeat a notice").
- **Edge case — the notice must not silently re-select a different theme on the user's behalf:** The orphaning detection **only** clears the applied theme to base; it never auto-picks another available custom theme as a "helpful" substitute, and — this is a deliberate judgment call — it does **not** clear `users.selected_theme_name` in the database. The stored value remains `'acme-brand'` so that if an admin later re-installs a theme file with that exact name, the user's original preference is honored again automatically without them having to re-select it. The `(app)/settings/themes/` page itself, when it detects the stored selection points at a currently-unavailable theme, shows it in the radio list as a distinct "acme-brand (currently unavailable)" disabled/greyed option rather than silently defaulting the radio group to "Default" — so the user isn't confused about what's actually stored vs. applied. Write a test asserting the DB row survives an orphaning event unchanged.
- **Edge case — the theme is re-installed with the same name before the user's next page load:** An admin removes and immediately re-adds `acme-brand.json` (identical `name`, possibly different token values) within the same reload cycle, or across two reload calls before Priya's next request. Since the orphaning check is re-evaluated live on every layout load (not cached/sticky), Priya simply sees `acme-brand` re-applied on her next page load — no dismissed-notice-suppression bug, no stale "orphaned" flag lingering once the theme is available again.
- **Edge case — every custom theme fails to load at once (e.g. `VAULT_THEMES_DIR` itself becomes unreadable, per 16.1 AC-2's operational-failure edge case):** This looks identical, from AC-3's perspective, to "all custom themes were removed" — any user with a non-null `selected_theme_name` gets the same orphaned-fallback treatment. No special-case handling needed; the check is purely "is my stored selection currently in the compiled set," regardless of *why* it isn't.

### AC-4 (added for completeness — not in epics.md): audit event on theme selection change

**Given** a user changes their selected theme (to a custom theme, or back to "Default"),
**when** the `PATCH /api/v1/themes/selection` request succeeds,
**then** an `AuditEvent.THEME_SELECTED` entry is written, scoped to the requesting user's current org context, following the exact fail-closed convention 16.1 established for `THEME_RELOADED` (`writeHumanAuditEntryOrFailClosed` inside the same transaction as the persisted selection — reuse, do not hand-roll a second audit-write path).

This AC is added because every other mutating endpoint in this codebase's Phase 2 work (14.x, 15.x, 16.1) writes an audit row on success, and a personal-preference change is still a real, forensically-relevant action (e.g. "did this user's own account make this change, or was their session compromised") — omitting it here would be an inconsistency, not a deliberate scope decision.

- **Happy path example:** Priya (org role `member`, no MFA requirement — see Dev Notes "no MFA gate for a personal-preference change") selects `acme-brand`. The transaction that writes `users.selected_theme_name = 'acme-brand'` also writes `AuditEvent.THEME_SELECTED = 'theme.selected'` with payload `{ themeName: 'acme-brand', previousThemeName: null }` (sanitized — theme *names* only, never token/CSS content, consistent with 16.1's "filenames and counts only" audit-sanitization precedent).
- **Edge case — audit write fails:** Following 16.1's fail-closed convention for authenticated endpoints (`secure-route.ts`'s `AuditWriteError` → `503 audit_write_failed`), a `PATCH /api/v1/themes/selection` call whose audit write fails must roll back the selection change and return 503 — the user's preference change must never silently succeed while going unaudited. Reuse `secureRoute()`'s built-in `writeAuditEvent` mechanism rather than a direct `writeHumanAuditEntryOrFailClosed()` call (unlike 16.1's reload endpoint, this endpoint's audit payload needs only the request body plus a `previousThemeName` lookup, which fits `writeAuditEvent`'s payload-callback shape cleanly — no need for 16.1's "generic path can't see the computed result" workaround).
- **Edge case — `THEME_SELECTED` is a new constant, not yet in the registry:** `packages/shared/src/constants/audit-events.ts` (confirmed via direct read, per the architecture-research pass for this story) contains `THEME_RELOADED: 'theme.reloaded'` but no `THEME_SELECTED`. Add `THEME_SELECTED: 'theme.selected'` following the same lowercase-dot-notation convention. Check `audit-events.test.ts` for any hardcoded exhaustive-list/count assertions and update them (same caveat 16.1's own AC-8 flagged).

### AC-5 (added for completeness): RBAC — any authenticated org member may select their own theme; no admin gate

**Given** theme *selection* (unlike theme *installation/reload*, which is OrgAdmin-only per 16.1) is a personal, per-user preference,
**when** `GET /api/v1/themes` and `PATCH /api/v1/themes/selection` are called,
**then** any authenticated member of the requesting org may call them for their own account — there is no `minimumRole`/`allowedRoles` gate beyond "is an authenticated member of this org" (i.e. `minimumRole: 'viewer'`, the lowest rank, per `apps/api/src/lib/secure-route.ts`'s `roleRank()` convention — `owner(3) > admin(2) > member(1) > viewer(0)`), and `requireMfa: false` (explicit, not omitted — per this codebase's convention of never leaving a route's MFA posture implicit).

- **Happy path example:** A `viewer`-role user (the lowest rank in this org) calls `PATCH /api/v1/themes/selection { "themeName": "acme-brand" }` and succeeds with `200` — viewers can brand their own view same as any other role, since this changes nothing about what they can read/write elsewhere.
- **Edge case — a user with no MFA enrolled at all (not just outside the grace period) still succeeds:** Unlike 16.1's `requireMfa: true` reload endpoint, this endpoint must **not** 403 an unenrolled user — selecting a personal color scheme has no security-sensitivity that would justify blocking non-MFA users from a core piece of app usability. Write an integration test explicitly asserting a non-MFA-enrolled `member` succeeds here (the mirror-image of 16.1's `routes.test.ts` MFA-gate-403 test), so a future refactor doesn't accidentally inherit `requireMfa: true` from copy-pasting 16.1's route config.
- **Edge case — cross-org isolation:** A user who is a member of Org A but not Org B cannot select a theme "for" Org B by manipulating a request — since the selection is per-user (not per-org, see AC-4/Dev Notes), the `PATCH` endpoint's request context is scoped by the authenticated session's *current* org membership (`ctx.auth.orgId`, resolved from the session the same way every other `secureRoute()` handler resolves it), and the stored `users.selected_theme_name` column has no `org_id` at all — there is no org-scoping bug surface to test here beyond confirming the endpoint uses the standard authenticated-session resolution and never accepts an org ID from the request body/params.

### AC-6 (added for completeness): concurrent access and session lifecycle

**Given** a user's selection must be visible to every one of their active sessions/tabs/devices without requiring them to re-authenticate,
**when** they change their selection in one tab,
**then** the change is durable (survives logout/login, new device, new tab) because it's read fresh from the DB on every `(app)` layout server load — never cached in the session/JWT itself.

- **Happy path example:** Priya selects `acme-brand` on her laptop. She then logs into the same account on her phone. The phone's first `(app)` page load reads `users.selected_theme_name` fresh from the DB (via the layout's server `load()` function, same request that resolves her auth session) and applies `acme-brand` immediately — no separate sync step, no stale value from a cached JWT claim.
- **Edge case — selection changes mid-session on another device:** Priya has two browser tabs open. She changes her selection in Tab A. Tab B does **not** update live (no websocket/SSE push for this — this codebase's existing SSE connection, per architecture.md's `(app)/+layout.svelte` "establishes SSE connection" pattern, is not extended to push theme-selection changes in this story; that would be meaningful scope creep for a low-stakes cosmetic preference). Tab B picks up the new selection on its next navigation/reload, same as any other server-loaded preference in this codebase that isn't SSE-pushed. This is an explicit, documented scope boundary, not an oversight.
- **Edge case — session expires / logout:** Logging out and back in has no effect on the stored preference (it's tied to the user's account row, not the session) — the next login's first `(app)` page load re-applies the same selection. No special session-lifecycle handling is needed beyond the standard authenticated-load pattern every other per-user setting in this codebase already follows.

### AC-7 (added for completeness): rate limiting

**Given** `PATCH /api/v1/themes/selection` is a low-risk, cheap (single-row UPDATE, no filesystem/validation work per call unlike 16.1's reload) authenticated action available to every role including viewer,
**when** rate-limiting this endpoint,
**then** apply `secureRoute()`'s standard default rate limit (60/min per the codebase default) rather than a stricter explicit one — there is no filesystem/CPU-heavy work per call here (unlike 16.1's `{ max: 10 }` reload, which does real per-call filesystem+validation work), so a stricter limit would only frustrate legitimate rapid experimentation (a user clicking through several themes to compare them) without a corresponding abuse-prevention benefit.

- **Happy path example:** A user clicks through all 3 available themes in under 10 seconds while previewing them. All 3 `PATCH` calls succeed — well within the default 60/min limit.
- **Edge case — scripted abuse (e.g. a compromised session hammering the endpoint):** At 61+ requests/min from the same session, the default rate limiter returns `429` same as every other `secureRoute()`-registered endpoint without an explicit override — no new rate-limiting logic needs to be written for this story, this AC exists purely to document *why* no explicit override was chosen (so a future reviewer doesn't wonder if it was an oversight).

### AC-8 (added for completeness): migration compatibility

**Given** this is the first story in Epic 16 to require a schema change (16.1's own Dev Notes explicitly flagged this: "16.2 will need a per-user preference column/table, which is where migration compatibility concerns will first arise in this epic"),
**when** adding `users.selected_theme_name`,
**then** the migration must be additive-only (a new nullable column with no default-value backfill needed, since `NULL` already means "base theme" — the correct default for every existing user row) and must not require any application-level backfill/dual-write period.

- **Happy path example:** New migration `packages/db/src/migrations/0058_users_selected_theme_name.sql`:
  ```sql
  ALTER TABLE users ADD COLUMN selected_theme_name TEXT NULL;
  ```
  (Confirm exact next migration number at implementation time — 16.1's Dev Notes cited `0057_organizations_default_locale.sql` as latest at the time of 16.1's writing; re-check `packages/db/src/migrations/` for the true current highest number before naming this file, since other stories may have landed migrations since.) Every existing user row gets `NULL` implicitly (no `UPDATE` statement needed) — meaning "base theme," which is exactly the correct pre-migration behavior for every user (nobody had a theme selection concept before this story shipped).
- **Edge case — no RLS policy needed for this column:** `users` is not an `org_id`-bearing table (it's a global identity table, confirmed via the same reasoning 16.1 used for why theme *files* need no RLS policy) — `check-rls-coverage.ts`'s CI guard only requires a `CREATE POLICY` for tables that have an `org_id` column; adding a nullable column to an existing non-`org_id` table triggers no new policy requirement. Confirm this against `packages/db/src/schema/users.ts`'s actual current column set at implementation time before assuming no RLS work is needed — if `users` unexpectedly does carry `org_id` (unlikely, but must be verified rather than assumed), this AC's "no RLS work" conclusion would need revisiting.
- **Edge case — rollback safety:** Since the column is nullable with no CHECK constraint and no foreign key, a rollback (`ALTER TABLE users DROP COLUMN selected_theme_name`) is safe and lossless from every angle except the (acceptable, cosmetic-only) loss of users' saved preferences — document this in the migration file's header comment, matching this codebase's existing migration-file documentation convention.

### AC-9 (added for completeness): operational logging

**Given** this codebase's convention (established by 16.1, 14.2, and others) of pairing every audit-worthy action with a lighter-weight operational log line for live-debugging visibility,
**when** a theme selection changes,
**then** log at `debug` level (not `info`/`fatal` — this is routine, high-frequency, low-severity activity, unlike 16.1's reload which logs at `info` for its summary line) a line noting the user ID and the new/previous theme name, using the existing `operationalLog()` helper — **no new `OperationalEvent` constant is needed** for the happy path, since this isn't an operational-failure signal the way 16.1's "themes directory unreadable" was; only add a new `OperationalEvent` entry if an actual failure mode surfaces during implementation that isn't already covered by a generic existing entry (e.g. if the DB write itself fails outside the audit-transaction path, which should already be covered by this codebase's generic DB-error logging).

- **Happy path example:** Priya's selection change logs `{"level":"debug","userId":"...","event":"theme_selection_changed","from":null,"to":"acme-brand"}` via the existing structured logger — visible in local/dev logs, filtered out of production `info`-level-and-above log aggregation by default (consistent with this being routine activity, not something an operator needs paged for).
- **Edge case — do not confuse this with the AC-4 audit event:** The audit event (AC-4) is the durable, compliance-relevant record (queryable via the audit log UI, retained per this codebase's audit-retention policy). This operational `debug` log line is a separate, ephemeral, log-aggregator-only signal for live debugging — do not conflate the two or try to satisfy AC-4 with only a log line (that would defeat the audit trail's purpose) or satisfy this AC by only writing the audit row (operators debugging live issues generally don't want to query the audit log for routine `debug`-level noise).

### AC-10 (added for completeness): tenant isolation / RLS

**Given** `users.selected_theme_name` has no `org_id` column and this codebase's RLS policies are enforced per `org_id`-bearing table (per `check-rls-coverage.ts`),
**when** verifying this story introduces no cross-tenant leak,
**then** confirm via an integration test that User A (org X) reading/writing their own selection can never read or affect User B's (org Y) selection, even though neither row carries an `org_id` — isolation here is achieved by scoping every query to `ctx.auth.userId` (the authenticated caller's own ID, never a client-supplied user ID), not by RLS.

- **Happy path example:** User A calls `PATCH /api/v1/themes/selection` — the handler resolves the target row via `ctx.auth.userId` from the session, never from a request body/param `userId` field (there is no such field in the request schema at all — the endpoint has no way to target another user's row even if a hostile client tried).
- **Edge case — explicit adversarial test:** Write an integration test using `withTestOrg()` twice (two separate org/user contexts, per this codebase's standard multi-tenant test pattern) asserting that User A's `PATCH` call followed by User B's `GET /api/v1/themes` never reflects User A's selection in User B's `selected` field — this is the direct analog of every other module's RLS-isolation test, adapted for a table whose isolation mechanism is "scoped by authenticated identity" rather than "scoped by `org_id` + RLS policy," since this table has no org dimension at all.

## Out of Scope (explicit — do not scope-creep)

- **An org-wide "default theme" that applies to anonymous/pre-auth users on the login screen** — the PRD's domain-requirements section (line ~641-648) frames theme selection as an administrator action ("Administrators select the active theme"), which conflicts with epics.md's Story 16.2 text ("As a user... for my view"). This story resolves that conflict in favor of epics.md's more specific, story-level Given/When/Then text (which uses "a user" three times and never mentions an admin/org-wide scope) plus Story 16.1's own Dev Notes, which already concluded "16.2 (per-user theme selection) is also user-scoped, not introducing org-scoped theme storage." An org-wide default (and its pre-auth login-screen implication from the PRD's Amara journey narrative) is a plausible future story but is **not** built here — flagged explicitly for a reviewer to confirm or challenge this reading, since it is the single largest judgment call in this story.
- **Live cross-tab/cross-device push of a theme-selection change** (AC-6) — no SSE/websocket extension for this; next navigation/reload picks it up, same as every other non-pushed per-user setting.
- **A UI theme *preview* mode** (seeing a theme applied without saving it) — epics.md's AC-2 describes select-and-save-immediately, not a separate preview step; not requested, not built.
- **Re-validating or re-surfacing 16.1's reload-failure reasons in this story's UI** — `(app)/settings/themes/` only ever lists themes that are currently in the *successfully compiled* set; a theme that failed validation never appears here at all (see AC-1's third edge case). Surfacing *why* a theme failed to install remains 16.1's admin-only reload-response concern.
- **Bulk/admin-driven theme assignment for other users** — this story's `PATCH` endpoint only ever targets the calling user's own selection (see AC-10); there is no "OrgAdmin sets everyone's theme" capability in this story.
- **Admin/support visibility into aggregate theme-selection data** (found via Stakeholder Round Table elicitation, Support/CS perspective — "if a user reports 'my theme looks wrong,' how does support see what they have selected without DB access?"): no admin-facing "which theme does user X have selected" or "how many users have theme Y selected" view ships in this story. The audit log (AC-4) technically has this data per-change-event, but there is no aggregate/current-state query surface. ## Dev Notes

- **Previous story intelligence (16.1, done):** 16.1 shipped `apps/api/src/modules/theming/{routes,service,schema}.ts`, the `POST /admin/themes/reload` endpoint, and `packages/shared/src/constants/theme-tokens.ts`. It explicitly deferred to this story: the theme-selection UI/API, the `(app)/settings/themes/` (not `(app)/admin/themes/` — see routing-convention note below) page, `apps/web/src/lib/theme/apply-theme.ts`, and the orphaned-theme fallback notice. Read 16.1's Dev Notes in full before starting — its module layout (flat, under `apps/api/src/modules/theming/`, sibling of `backup/`/`admin/`), its `service.ts`'s in-memory `getCompiledThemes()`-shaped output, and its audit-write pattern are all direct dependencies of this story.
- **Routing-convention correction (found via architecture research for this story):** architecture.md's own Requirements-to-Structure table still lists theming's page under `(app)/admin/themes/` and flags it "unconfirmed." Direct inspection of `apps/web/src/routes/` confirms **no `(app)/admin/` directory exists anywhere in this repo** — the actual convention (already corrected for the `extensions` row in the same table, per Story 14.x precedent) is `(app)/settings/*` for user/org-facing settings pages and `(app)/platform/*` for instance-operator pages. Since this story's page is a **personal** setting (not an OrgAdmin-only page), it belongs under `(app)/settings/themes/`, matching `(app)/settings/language/`'s pattern (a personal preference page, not an admin-gated one like `(app)/settings/sso-domains/`) more closely than the admin-gated precedent. Confirm `(app)/settings/language/`'s exact structure at implementation time as the closest analog (personal preference, no role-gate, single-select-immediate-save) — closer than `sso-domains`/`extensions`, which are both OrgAdmin-gated and therefore structurally different (they need a `canManage*()` role-gate helper this story does not).
- **Scope judgment call: per-user vs. per-org selection (the single biggest open question in this story — flagged explicitly for review).** Two source documents disagree: `prd.md`'s domain-requirements section says "Administrators select the active theme from the base theme plus any installed custom themes" (org-wide, admin-controlled), while `epics.md`'s Story 16.2 Given/When/Then text says "As a user, I want to choose which installed theme is active for my view" (personal, per-user) — using "a user" and "my view," never "administrator" or "the organization's." This story resolves the conflict in favor of the epics.md story-level text (the more specific, more recently-authored, story-scoped source) plus 16.1's own Dev Notes, which already independently concluded "16.2 (per-user theme selection) is also user-scoped, not introducing org-scoped theme storage." This means: no org-wide default theme, no effect on the pre-auth login screen (which the PRD's Amara journey narrative implies should carry org branding — that narrative is **not** fully satisfiable by this story's scope as written, and is called out in Out of Scope). **If a reviewer disagrees with this reading**, the correct fix is an org-level `organizations.default_theme_name` column (mirroring 15.2's `organizations.default_locale` precedent) as a *fallback* layered under this story's per-user override — but that is a larger, separate change and is deliberately not built speculatively here.
- **RBAC convention note (relevant to Story 14-8's now-documented convention — see memory):** 16.1's own reload endpoint uses `allowedRoles: ['owner', 'admin']` (a contiguous-from-the-top array, which architecture.md's now-documented RBAC convention — added in Story 14-8 — flags as a lint violation without an inline "why excluded" comment; `minimumRole: 'admin'` is the correct form for that shape). This story's endpoints use no role gate beyond `minimumRole: 'viewer'` (i.e., "any authenticated org member"), so the contiguous-array pitfall doesn't arise here — but don't copy 16.1's `allowedRoles` shape as a habit; use `minimumRole` per the documented convention.
- **RLS/tenant isolation:** `users.selected_theme_name` has no `org_id` — isolation is via `ctx.auth.userId` scoping, not RLS (see AC-10). Confirm `packages/db/src/schema/users.ts`'s actual columns at implementation time rather than assuming; if `users` turns out to carry `org_id` (would be surprising given every other module's references to it as a global identity table), this story's "no RLS policy needed" conclusion and its migration plan both need revisiting before merge.
- **Auth/session lifecycle:** No MFA gate (explicit `requireMfa: false`, not omitted) — this is a low-stakes cosmetic preference, unlike 16.1's `requireMfa: true` admin action. Selection is read fresh from the DB on every `(app)` layout load, never cached in the session/JWT (AC-6) — this keeps multi-device/multi-tab behavior simple and correct without needing session invalidation on a preference change.
- **Concurrent access:** No optimistic locking / version column needed — repeated or near-simultaneous writes of the same or different `themeName` values by the same authenticated user are simply last-write-wins, since there is no meaningful "conflict" to detect (see AC-2's double-submit edge case).
- **Migration compatibility:** This is Epic 16's first schema change (flagged in advance by 16.1's own Dev Notes). Purely additive (`ADD COLUMN ... NULL`), no backfill, safe rollback (see AC-8).
- **Operational logging:** `debug`-level line per selection change (AC-9) — deliberately lower severity than 16.1's `info`-level reload-summary line, since this is routine per-user activity, not an admin/ops-relevant event.
- **Testing standards:** Mirror 16.1's `apps/api/src/modules/theming/routes.test.ts` conventions (RBAC/role tests, `withTestOrg()` for integration tests, `bootstrapRouteIntegrationTest()`'s MFA-grace-period handling — this story needs the *inverse* assertion, i.e. that a non-MFA-enrolled user succeeds). Web-side, mirror `sso-domains-page.test.ts`/`extensions-page.test.ts`'s two-file convention (`{name}-page.test.ts` for component behavior, `{name}-page.server.test.ts` for the load function), adapted for a page with no disallowed-role state (this page has none — every authenticated org member can access it).
- **`GET /api/v1/themes` response shape does not use the `{ data, meta }` collection envelope (found via Self-Consistency Validation elicitation, checked against architecture.md's own response-format conventions, lines 805-818):** that envelope is documented for paginated/large collections; the compiled-themes list is a small, bounded, non-paginated set (realistically a handful of entries, capped implicitly by how many files an admin drops in `VAULT_THEMES_DIR`), so a flat `{ themes: [...], selected: string | null }` body is consistent with this codebase's other small-fixed-set responses (e.g. 16.1's own `{ loaded, failed }` reload response, which is also an unwrapped flat shape) rather than a mismatched pagination-shaped wrapper around data that never paginates.
- **Security Audit Personas pass (hacker + defender + auditor) confirmed no exploitable secondary injection surface:** the hacker persona's most promising angle — supplying a hostile `themeName` string to `PATCH` hoping it reaches the compiled CSS or an HTML attribute unsanitized — fails because `themeName` is rejected unless it already exactly matches an entry in the *already-CSS-injection-hardened* (by 16.1's AC-4) compiled-themes list; there is no path for arbitrary client-supplied text to reach either the audit payload beyond a bounded/validated string or the rendered `data-theme` attribute. The defender/auditor personas' main finding was procedural, not code-level: keep the Zod `max(100)` bound (added to AC-2 above) so a malformed request is rejected cheaply and consistently, rather than relying solely on the (also-correct, but more expensive) list-membership check.
- **RBAC convention self-consistency check (Story 14-8's documented `minimumRole`/`allowedRoles` convention):** confirmed this story's `minimumRole: 'viewer'` usage is the correct contiguous "this rank or higher" form and needs no `allowedRoles` exception or inline comment — unlike 16.1's `allowedRoles: ['owner','admin']`, which the convention (formalized after 16.1 shipped) would flag as needing to be `minimumRole: 'admin'` instead. This story does not fix 16.1's existing route in passing (out of scope — a drive-by refactor of a merged, done story's route is not this story's concern), but the inconsistency is noted here so a future cleanup pass (or the next epic-16 retro) has a pointer to it.
