### 3. [High] RBAC mechanism choice (`minimumRole` vs `allowedRoles`) independently re-derived three times within this epic, with no documented convention anywhere

`14-2` chose `allowedRoles: ['admin']` (owner excluded), explicitly calling it a judgment call
(`14-2-load-a-configured-extension-at-startup-fail-safe.md:163`). `14-5` mirrored it verbatim
(`14-5-extension-status-admin-page.md:69`). `14-6` diverged to `minimumRole: 'admin'` (rank-based, owner
**included**), citing `organization-settings-routes.ts`'s pattern instead, and its own Dev Notes state:
*"do not silently pick one without documenting the choice"* (`14-6-org-sso-domains-admin-ui.md:76,161`).
`grep -rn "minimumRole\|allowedRoles" _bmad-output/planning-artifacts/architecture.md` returns zero
hits — no ADR or documented convention exists anywhere for when to use which mechanism. The
inconsistency isn't confined to epic 14 either: `apps/api/src/modules/org/routes.ts` itself mixes
`allowedRoles: ['owner', 'admin']` (lines 97, 122), `allowedRoles: ['admin', 'owner']` (lines 166, 218,
341 — inconsistent member ordering in the same file), and `minimumRole: 'admin'` (lines 411, 439, 579)
with no stated rule distinguishing them. Each individual divergence was honestly flagged in its own
story ("do not silently pick one without documenting"), but the flag itself was never converted into a
lasting rule — structurally the same "flagged-but-never-promoted-to-a-convention" failure mode that hit
`P5-1` (z.union ordering) for 3 occurrences before Epic 15's session finally fixed it (Finding 5).
**Resolution:** Write a short convention (a new architecture.md subsection or a standalone ADR) stating
when to use `minimumRole` vs `allowedRoles` (e.g., "use `minimumRole` for a single-threshold admin gate;
use `allowedRoles` only when the permitted set is non-contiguous in the role hierarchy"), and retrofit
`org/routes.ts`'s existing ordering inconsistency at the same time. Offered as a follow-up story below.

## Key Takeaways

1. Epic-level rollup drift can go in either direction (ahead of or behind story reality) — both need the
   same fix discipline, not just the "story finished, forgot to flip the epic" direction this project has
   mostly seen before.
2. A judgment call flagged honestly in a story's Dev Notes is not the same as a resolved convention —
   flagging without promotion has now caused two multi-occurrence patterns (`z.union` ordering, RBAC
   mechanism) in this project's history.
3. Verify "resolved" claims against disk, always — this retro's own research nearly re-flagged two items
   that were fixed in the same session by a concurrent worktree, which is exactly the kind of
   false-resolved claim this skill's evidence requirement exists to prevent.
