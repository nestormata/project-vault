# Story 17.2: Share a Credential with an External Recipient via Secure Link

Status: ready-for-dev

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a project member with reveal access to a credential,
I want to share that credential's current value — or a specific field of a multi-field secret — with someone **outside my organization** (no account, no login) via a bounded-duration, single-use-or-time-boxed link that requires me to step up my own authentication before I can create it,
so that I can hand a secret to an external contractor/vendor/support engineer without giving them a Project Vault account, while the product still gives me full audit visibility and my org's admins stay informed that an unauthenticated access pathway to secret material now exists.

### Persona journey stub

**Morgan (project member)** opens a credential detail page for a credential they can reveal, clicks **Share**, toggles the recipient type from "org member" (17.1) to **"external (email)"**, types the recipient's email address, sets an expiry (or accepts the default — shorter than 17.1's, see AC-5), optionally toggles "single view only" (defaults to `true` and cannot be turned off for external recipients — see AC-5), and clicks **Create share link**. Before the share is created, Morgan is prompted to **re-enter their password or a fresh MFA code** (step-up re-authentication, AC-3) — creating an unauthenticated access pathway to secret material is treated as sensitive enough to require this even though normal reveal doesn't. Once step-up succeeds, Morgan sees the generated link once (masked/copy-once affordance) and a confirmation that no in-app notification goes to the external recipient (Morgan must send the link themselves, e.g. via email) but that org admins have been notified a new external share was created.

**Priya (the external recipient, has no Project Vault account)** receives the link (out of band — email, Slack, however Morgan sends it) and opens it in a browser with **no login prompt**. Priya lands on a public, unauthenticated **consent page** that names the credential, the sharer, and the field (if scoped) but shows no secret value and performs no state-changing action on load — a chat-client link-unfurling bot or an email "safe link" prefetcher that fetches this same URL automatically burns nothing (AC-9). Priya clicks an explicit **"Reveal secret"** button, which POSTs to the reveal endpoint and shows the value. If the link is single-use (the default and, for external recipients, the only option), a second open of the same link shows "This link has already been used" instead of the value. If the window has expired, Priya sees "This link has expired." The page sets `Referrer-Policy: no-referrer` on its own document response (not just the API) and loads no third-party resources, so nothing about the token-bearing URL can leak via an outbound `Referer` header (AC-10, F1).

Org admins receive an in-app/email alert (existing FR100 routing) both when Morgan creates the external share and again the first time Priya actually views it (AC-12) — creation-only notification would leave admins blind to whether a live external link was ever actually exercised.

Morgan's existing **Shares** tab (built in 17.1) now also lists external shares mixed in with member shares, showing the recipient's email instead of a member name, and offers the same **Revoke** action.

## Acceptance Criteria

1. **Recipient is an external email address, not an org member.** The share-creation endpoint (a new sibling to 17.1's `POST /:projectId/credentials/:credentialId/shares`, or an extension of the same endpoint accepting a `recipientType` discriminator — dev agent's call, documented in the Dev Agent Record) accepts `recipientEmail` (a validated email address) instead of `recipientUserId`. The created row has `recipient_type = 'external'`, `recipient_email` set to the (lowercased/trimmed) address, and `recipient_user_id = NULL`. Example: Morgan shares field `api_key` of credential "Stripe Prod" with `priya@vendor.example` — the row has `recipient_type='external'`, `recipient_email='priya@vendor.example'`, `recipient_user_id=NULL`, `field_key='api_key'`. Edge case: an email that happens to match an existing org member's address is still stored as an external share (this endpoint never resolves email → `recipient_user_id`; if Morgan actually meant to share with a teammate, that's 17.1's `recipientUserId` flow, and mixing the two is a UI-level user-education problem, not something this endpoint silently "fixes" by resolving the address).

2. **Share creation eligibility reuses the same reveal gate as 17.1 (and normal reveal).** A user can create an external share only if their effective project role would pass `rejectIfInsufficientProjectRoleForReveal(..., kind: 'reveal')` (`apps/api/src/modules/credentials/routes.ts`) — identical to 17.1's AC-1, no looser check for the external path even though it's a different recipient type. Example: a `viewer`-role project member attempting to create an external share gets the same `403 INSUFFICIENT_PROJECT_ROLE` a `viewer` gets attempting normal reveal or an internal share.

3. **Sharer step-up re-authentication is required at creation time.** This is new versus 17.1 and is the epic security review's Round 1 finding, applied here for the first time in this codebase (no existing step-up/re-auth primitive exists — confirmed by codebase search; the closest analogues are login-time password verification (`apps/api/src/modules/auth/password.ts#verifyUserPassword`) and login-time TOTP verification (`apps/api/src/modules/auth/mfa-login.ts#verifyConfirmedLoginTotp`)). Concretely: the create-external-share request body must include **either** a `password` field (verified against the sharer's own stored hash via `verifyUserPassword`) **or**, if the sharer has MFA enrolled, a `totpCode` field (verified via the same TOTP-verification primitive `mfa-login.ts` uses at login, reused rather than reinvented) — the caller supplies whichever factor they have. This is a **synchronous, stateless re-check on this single request** (no new "step-up session"/short-lived elevated-privilege token is introduced — that would be meaningfully more work and is explicitly out of scope; document this as a deliberate scope decision in the Dev Agent Record, the same way 17.1 flagged its "no MFA on share creation" decision). A missing/incorrect factor returns `401 step_up_required` (distinct code from generic auth failure) with no share created and no partial side effects. **Failed step-up attempts are rate-limited (surfaced by Failure Mode Analysis during advanced elicitation):** this endpoint accepts a live password/TOTP guess from an already-authenticated session, which is a brute-force surface against the sharer's own credential that didn't previously exist at this granularity (login has its own rate limiting, but this is a *second*, independent guessing endpoint for the same secret) — reuse this codebase's existing `secureRoute` `rateLimit` mechanism (same shape 17.1 used for its revoke route) scoped tightly on this route, e.g. a handful of attempts per minute per session, returning `429` once exceeded rather than continuing to accept guesses. This is distinct from AC-22's per-token reveal-attempt cap (that one protects the *recipient-facing* reveal endpoint; this one protects the *sharer's own credential* from being brute-forced via the creation endpoint). **If the sharer has no MFA enrolled**, the `password`-only path is accepted (password re-entry is always available; MFA is an *additional* accepted factor, not a hard requirement to use this feature at all — requiring MFA enrollment as a precondition would make external sharing unusable for any org that hasn't rolled out MFA, which is out of proportion to this story's scope). Example: Morgan (no MFA enrolled) supplies their current password in the request body; it verifies; share creation proceeds. Counter-example: Morgan supplies a stale/wrong password → `401 step_up_required`, nothing persisted. Counter-example: Morgan has MFA enrolled and supplies an already-used or expired TOTP code → same `401`, reusing the existing TOTP-replay-prevention table (`totpUsedCodes`) rather than a parallel mechanism.

4. **Field scoping reuses 17.1's `field_key` model unchanged.** Same `NULL` = whole-credential, non-null must match a current template field key at creation time, same auto-expire-on-field-removal-or-rename semantics as 17.1's AC-3 (validated the same way, via `validateFieldKey`/`fieldMetaForResponse`, reused verbatim — no new field-validation code path). Example: sharing field `db_password` of a multi-field secret; if that field is later renamed to `database_password` (Story 13.2 rename) before Priya views the link, her next GET/reveal attempt on the old field key resolves as expired (same "treat missing field as expired, never a 500 or silent null" contract 17.1's `revealShare`/`revealCurrentValue` already implements — reused, not reimplemented, for the external path).

5. **Bounded duration, single-use only (tighter than 17.1 by design).** At creation, the sharer sets `expiresAt` (required, future, server-enforced max). **Reasoned default, a judgment call for the dev agent to document in the Dev Agent Record (same convention as 17.1's `SHARE_DEFAULT_TTL_MS`/`SHARE_MAX_TTL_MS`):** default **1 hour**, capped at **72 hours (3 days)** — materially tighter than 17.1's 24h default / 7-day cap, because an external link has no account behind it at all (anyone who obtains the URL — forwarded mail, a compromised inbox, a shared inbox, a "safe link" scanning proxy that stores the URL) can use it, versus 17.1's link which still requires the *correct authenticated org member's session* even if forwarded. **`singleUse` is not a caller-controlled option for external shares — it is hard-coded to `true` server-side** (the request body must either omit it or pass `true`; passing `false` is a `400 external_share_must_be_single_use`), unlike 17.1 where multi-view is a real, honored option. Rationale: a multi-view, long-lived, unauthenticated bearer link is the single highest-risk configuration this feature could produce, and nothing in the product requirement (FR122/FR123) demands multi-view for the external case — 17.1's org-member path already covers the "hand off ongoing access to a known person" use case via an authenticated, revocable, re-checked-at-view session binding that the external path structurally cannot offer. Example: `expiresAt` 30 minutes out, single-use — one successful reveal by Priya, then any further open shows "already been used." Edge case: sharer omits `expiresAt` entirely → `400` (required, same as 17.1); sharer requests 5 days out → `400 expires_at_invalid: too_far_in_future` (72h cap, not 17.1's 7-day cap).

6. **Revocation mirrors 17.1.** The sharer (or any org admin/owner) can revoke an `active`/`pending` external share at any time before it's viewed or expires, reusing `revokeShare` (already generic over `recipient_type` — confirmed by reading `apps/api/src/modules/credential-shares/service.ts`: `revokeShare`/`findShareInScope` filter only by `orgId`/`credentialId`/`shareId`/`status`, never by `recipient_type`). Revoking an already-viewed/expired/revoked share is the same idempotent no-op as 17.1's AC-5. **Reuse `revokeShare`, `findShareInScope`, and the revoke route's now-fixed auth-before-mutate ordering (PR #251, see Previous Story Intelligence) verbatim** — do not write a second revoke function for the external path.

7. **The `credential_shares` table needs no new migration for schema shape** — 17.1's migration `0059_credential_shares.sql` already created `recipient_type`, `recipient_email`, and every other column this story needs. This story's DB-layer work is entirely about **RLS**, not schema: the org-scoped RLS policy on `credential_shares` (applied by migration 0059, standard `orgScoped` pattern) assumes every query runs inside a session that has already called `set_config('app.current_org_id', ...)` — which is only ever set from an **authenticated** request's resolved `orgId` (see `apps/api/src/middleware/rls.ts#setRlsOrgContext`). An external recipient has no session and therefore no `orgId` to set *before* the token lookup resolves which org the share even belongs to — this is the "org unknown until token resolves" problem, and it needs a documented, narrow exception (see AC-8 for the concrete mechanism; this AC is the acknowledgement that one is required, distinct from 17.1's Dev Notes explicitly saying **no** RLS exception was needed there).

8. **Tokenized bearer-link access — no session required, org context established purely from the token.** This is the core architectural difference from 17.1. Concrete mechanism (reusing an existing precedent in this exact codebase, not sessions/refresh_tokens — see Dev Notes for why that precedent is the wrong shape here — but `apps/api/src/modules/monitoring/public-status-page-routes.ts` + `status-page-service.ts#findStatusPageByTokenHash`, Story 6.3's public status-page token pattern): the external access routes are registered with `secureRoute(..., security: { requireAuth: false, ... })` (the same flag `publicStatusPageRoutes` uses). The token-lookup step runs on the **admin DB connection** (`getAdminDb()` from `apps/api/src/lib/db.ts`, which bypasses the org-scoped RLS session variable entirely, exactly as `findStatusPageByTokenHash` does) to find the `credential_shares` row by `token_hash` — this is the one, narrow, explicitly-justified place an unauthenticated request touches this table without RLS scoping, and it is a single indexed point-lookup by hash, not a scan. Once the row (and therefore `orgId`) is resolved, every subsequent read/write in the same request (credential/field lookup, the atomic reveal claim, the audit write) re-scopes via `withOrg(orgId, ...)` exactly like `getPublicStatusPageServices` does in step 2 of the status-page pattern. Example: `GET /api/v1/external-shares/access/:token` resolves `token_hash` → row on the admin connection, learns `orgId = 'abc'`, then does everything else inside `withOrg('abc', tx => ...)`. Edge case: token hashes to no row at all → same generic 404 the malformed/expired/revoked cases return (see AC-17).

9. **Two-step reveal, and the first GET must be provably inert.** The link's first `GET .../access/:token` returns metadata only (credential name, sharer display name — not email, to avoid leaking an org member's address to an unauthenticated party — field if scoped, expiry) and **must not** transition the share's status, increment `view_count`, or set `first_viewed_at` — a link-unfurling crawler (Slack/Teams/Outlook "Safe Links", email prefetchers) that automatically fetches the URL the instant it's posted must not burn the single-use claim before Priya ever opens it (epic security review §1.3, Round 1 finding). Reveal happens only on an explicit `POST .../access/:token/reveal` triggered by Priya's button click. Example: Slack's link-unfurler fetches the metadata GET the moment Morgan pastes the link into a channel — this is expected, harmless traffic; the share remains fully `pending`/`active` and Priya's later click still succeeds. Contrast with 17.1, where the metadata GET is also inert but the *threat* (an authenticated org member's own client prefetching their own link) was never the point of building it that way for 17.1 — for 17.2 this specific inertness requirement is itself a named, tested AC, not an incidental byproduct.

10. **`Referrer-Policy: no-referrer` on BOTH the API responses and the page's own HTML document response, verified from the start — not just the API.** 17.1 shipped with `Referrer-Policy` set on its API JSON responses but *not* on the `/shares/[token]` page's own document response (the actual browser-navigated URL that carries the raw token) — a real gap caught only in post-merge adversarial code review and fixed in commit `9713a1a` ("fix(credential-shares): revoke auth-bypass, single-use burn, missing Referrer-Policy") via `+page.server.ts`'s `load` calling `setHeaders({ 'Referrer-Policy': 'no-referrer' })`. **This story's dev agent must set that header on the new external consent/reveal page's own `+page.server.ts` `load` function from the first implementation, not just on the API routes** — this AC exists specifically so that mistake is not repeated. Additionally (F1, epic security review): the consent/reveal page must load **no third-party-origin resources** (no external images, fonts, scripts, analytics, embeds) — any such resource's own outbound request could carry the page's URL (and thus the token) via its `Referer` header even with `no-store`/`no-referrer` set on the *page's own* response, since `Referrer-Policy` governs what the page's own outbound requests send, and a same-origin-only resource set is the only way to guarantee zero leak surface. Verify via a test asserting the response header, mirroring 17.1's regression test for the same header (`share-access-page.server.test.ts`).

11. **Full audit trail (FR124) — no new audit event types.** Reuses `CREDENTIAL_SHARE_CREATED` / `CREDENTIAL_SHARE_VIEWED` / `CREDENTIAL_SHARE_REVOKED` verbatim (`packages/shared/src/constants/audit-events.ts` — already defined by 17.1, confirmed unchanged). Every audit payload written for an external share includes `recipientType: 'external'` (and, for creation, `recipientEmail` — never for the view/reveal audit entry, to avoid persisting the recipient's address into every audit row beyond the one place it's needed) so audit log readers can distinguish external from member shares without a schema change; this is the one external-specific tag this story adds to existing audit payload shapes, not a new event type.

12. **Admin notification on BOTH creation and first view (new versus 17.1).** 17.1 only notified the *recipient* (an org member, via `dispatchDirectUserNotification`) on creation. External recipients have no in-app notification target at all (no account), so this story instead implements the epic's own admin-notification requirement: `dispatchOrgAdminNotification` (`apps/api/src/notifications/dispatcher.ts`, the existing FR100 routing already used elsewhere, e.g. security alerts) fires (a) once at share creation — "An external share was created for credential X by <sharer>, expiring at <t>" — and (b) once at first successful reveal — "An external share for credential X was viewed by its recipient at <t>" (never fires again for a single-use share, since there's only ever one view; not applicable for repeat views since AC-5 hard-codes `singleUse: true`). Both are best-effort, non-blocking (same AC-18 pattern as 17.1: a notification-dispatch failure never blocks or rolls back share creation or the reveal itself — the recipient still gets their value, admins get a warning-level log entry instead of visibility, same tradeoff 17.1 already made explicit).

13. **Atomic single-use claim (F2) — reuse `claimSingleUseView` exactly, verified generic over `recipient_type`.** Reading `apps/api/src/modules/credential-shares/service.ts` confirms `claimSingleUseView(tx, shareId)` is a bare `UPDATE credential_shares SET status='viewed', ... WHERE id = $1 AND status = 'active' RETURNING *` with no `recipient_type` filter anywhere — it is already fully generic. This story must call this exact function (not write a parallel "external claim" function) from its own reveal-service code, inside the `withOrg`-scoped transaction described in AC-8. Two concurrent reveal POSTs for the same external link must not both succeed — the loser gets the same "already used" terminal response a genuinely later request would get, exactly like 17.1's AC-14.

14. **Sharer deactivation implicitly revokes outstanding external shares too (F6) — verify, do not re-implement.** Reading `apps/api/src/modules/credential-shares/service.ts#autoRevokeSharesForDeactivatedUser` confirms its `WHERE` clause filters only on `orgId`/`sharedBy`/`status = 'active'` — **no `recipient_type` filter** — so it already revokes a deactivated user's outstanding external shares alongside their member shares, with no extension needed. This AC exists to require the dev agent to confirm this by reading the function (as this Dev Notes section already has) and add one regression test asserting a deactivated sharer's `pending` external share transitions to `revoked`, rather than silently assuming it and leaving the external path untested by Story 4-3's deactivation flow.

15. **No org-membership check applies to the recipient (there is none) — but the sharer's continued active org membership gates link validity, per F6's spirit extended.** Unlike 17.1's AC-16 (re-check recipient membership/active-status at view time), an external recipient was never an org member, so that check is structurally N/A here. What **does** apply: if the sharer's own account is deactivated between share creation and Priya's reveal attempt, AC-14's deactivation hook has already flipped the share to `revoked` by the time she clicks reveal (not a separate "check sharer status live at reveal time" code path — the deactivation-time revoke is the enforcement mechanism, consistent with how 17.1 handles this for the sharer side too). Document this explicitly as "N/A by design, not an oversight" in the Dev Notes/Dev Agent Record, since a reviewer unfamiliar with the asymmetry might otherwise flag its absence as a gap.

16. **Org-level cap on concurrent pending external shares per credential/field (F3).** No per-org configurable settings table precedent fits this cleanly — `system_settings` (`packages/db/src/schema/system-settings.ts`) is a single platform-wide singleton row (`CHECK (id = 1)`), used for genuinely platform-global values like `maxOrgs`; it is not a per-org limits table, despite the security review's shorthand description of it as "the pattern already used for other org limits." **Reasoned judgment call for the dev agent (document in Dev Agent Record, same convention as 17.1's TTL defaults):** implement this as a fixed code constant, e.g. `MAX_PENDING_EXTERNAL_SHARES_PER_FIELD = 5` (mirroring `SHARE_DEFAULT_TTL_MS`/`SHARE_MAX_TTL_MS`'s shape in `apps/api/src/modules/credential-shares/schema.ts`), counting `credential_shares` rows with `recipient_type = 'external'`, matching `(credentialId, fieldKey)` (treating `fieldKey IS NULL` as its own bucket, i.e. whole-credential shares count separately from any specific field's shares), and `status IN ('active','pending')` at creation time. Exceeding the cap returns `429 external_share_cap_exceeded` (429, not 409 — this is a rate/volume limit on a specific caller-triggerable action, not a conflicting-state error, consistent with this codebase's existing use of 429 for rate-limit-shaped rejections elsewhere). Example: 5 active external shares already exist for credential X's `api_key` field; a 6th creation attempt (even by a different sharer) gets `429`; revoking or letting one of the 5 expire immediately frees a slot for a subsequent attempt. Building a genuine per-org-configurable version of this cap (a new settings surface) is out of scope — flag as a deliberate scope decision if Nestor wants it configurable later.

17. **Timing-safe token lookup (F4) — always hash + query unconditionally.** The token-lookup function for the external path must never short-circuit before hashing the presented token (e.g. no early-return on "token doesn't look like valid base64url" before the hash+query runs) — every request, regardless of whether the token is malformed, well-formed-but-never-existed, expired, revoked, or valid, takes the same code path: hash → query by `token_hash` → branch on the query result. This mirrors 17.1's `findShareByToken`'s existing `constantTimeHexEqual` defense-in-depth comparison (reuse that same constant-time-compare helper for the external path's hash-equality check too, not just the DB `WHERE` clause's own equality). All not-found/expired/revoked/malformed cases collapse to the identical `404` response shape and, so far as achievable in Node/Postgres, the same rough latency profile — no distinguishing "the hash matched a row that turned out to be expired" from "the hash matched nothing at all" via response shape, status code, or an obviously different code path length. Example test: assert a garbage 5-character string and a validly-shaped-but-never-issued 32-byte token both hit the hashing code path (verifiable via a spy/counter in tests, not by timing assertions which are inherently flaky in CI).

22. **Per-token reveal-attempt cap, auto-revoking on exceed (epic security review §1.6 — surfaced by advanced elicitation, was named in the source design doc but missing from the initial AC draft).** The reveal endpoint (`POST .../reveal`) enforces a small per-share attempt cap — a **judgment call for the dev agent, document in the Dev Agent Record**: recommend **5 failed reveal attempts** (an "attempt" here means a `POST .../reveal` call that reaches the atomic-claim step and loses — i.e. the token hash matched a row but the claim failed because the share was already terminal, NOT a mismatched-token-hash call, since that would let an attacker exhaust a *different*, unrelated share's budget by guessing garbage tokens; track the counter keyed by the resolved `shareId`, only incrementable once the token has already resolved to a real row). On exceeding the cap, the share transitions to `revoked` (same terminal state a manual revoke produces, audited with a distinguishing reason e.g. `attempt_cap_exceeded`) — this closes brute-force guessing of a valid-but-unguessed token down to a bounded number of tries, on top of the token's own 256-bit entropy making guessing infeasible in the first place (defense-in-depth, not the primary control). **Two design constraints from Challenge-from-Critical-Perspective review, both required to avoid undermining AC-17's enumeration-resistance:** (a) the response body/status must never reveal the remaining-attempts count or that a cap exists at all — the caller sees the same generic "invalid or expired link" shape whether they hit attempt 1 of 5 or the cap-triggering attempt, otherwise the counter itself becomes a new oracle an attacker can use to distinguish "a real token I haven't cracked yet" from "garbage"; (b) the inert metadata `GET` (AC-9) must **never** increment this counter — only `POST .../reveal` attempts count, so a link-unfurling crawler fetching the consent page repeatedly, or Priya innocently reloading the consent screen before clicking reveal, cannot trip the cap and lock out the real recipient. Example: an attacker who somehow narrows a token to a small guess-set makes 5 reveal attempts against the real share, all failing (wrong token doesn't even resolve to this row, so doesn't count — see above) — this AC only bites once an attacker has a token that *does* resolve to a row but keeps losing the atomic claim race or hitting a since-changed state; realistically this fires almost only when the share is already legitimately consumed/expired and something keeps retrying, which is fine to auto-revoke. Counter-example: Priya's browser retries the reveal POST 3 times due to a flaky network connection before finally succeeding on the 4th — each *failed* attempt (timeout/5xx before reaching the claim) does not count against the cap (only a request that reaches the atomic-claim step and observes a non-`active` status counts), so this does not lock her out.

18. **Redact the raw token — and the step-up `password`/`totpCode` — from structured request logs (F5, extended by advanced elicitation).** Audit via `req.log`/pino's structured logging: confirm (a) whether Fastify's request logging serializes the URL/params/body by default (check `apps/api/src/app.ts`'s logger configuration) and (b) whether the token param, or the step-up creation route's request body, appears in any `req.log.*` call this story's own route handlers make (e.g. error-path logs that dump `req.params`/`req.url`/`req.body` wholesale). Any such call must explicitly redact by name: the `token` path parameter (external-access routes), and the `password`/`totpCode` body fields (the new step-up creation route, Task 2) — the security review's F5 named only the token, but the step-up factor is at least as sensitive (it's the sharer's actual account password or a live TOTP code) and this story introduces that field for the first time in this endpoint's request shape, so it needs the identical redaction discipline from its first commit, not a follow-up fix. This is a repo-wide logging-hygiene check scoped to this story's new files, not a rewrite of the global logger config, unless the audit finds the global config already leaks full request bodies (flag as a separate finding if so, don't silently expand scope).

19. **`token_hash` uniqueness — already enforced, confirm only.** 17.1's migration already added `idx_credential_shares_token_hash` as a `uniqueIndex` covering the whole table regardless of `recipient_type`. No new work; add one test creating an external share and asserting the same unique-constraint behavior 17.1 tested for member shares (defense-in-depth, not expected to ever actually collide by construction).

20. **Archival guard extension — already generalized, confirm only.** 17.1's `findBlockingShareIds` (`apps/api/src/modules/projects/archive-guards.ts`) already blocks/requires-confirmation on archiving a project/credential with any `active` share, and — per the sprint-change-proposal's Round 3 finding — was already written to cover "staged rotations and active shares" as a class, not filtered by `recipient_type`. Confirm by reading the function (it queries `credential_shares` filtered only by `status = 'active'`/`credentialId`, per 17.1's implementation) and add one regression test with an active *external* share to close the gap in test coverage 17.1 left (17.1 only tested member shares against this guard).

21. **Web UI: a new, public, UNAUTHENTICATED consent/reveal route — a new SvelteKit route group, not the existing `(app)` group.** Contrast with 17.1's `/shares/[token]` which lives under the authenticated `(app)/...` route group (requires a logged-in session to even load). This story needs a route like `/external-shares/[token]` living in its **own route group** with its own root `+layout.svelte` (no logged-in-user chrome — no nav sidebar, no account menu, nothing that assumes `locals.user` exists) and its own `+layout.server.ts` that does **not** call whatever `(app)`'s layout uses to enforce/read a session (verify by reading `apps/web/src/routes/(app)/+layout.server.ts` for what to explicitly *not* inherit). - **Reuse map — what to call verbatim vs. what needs a new sibling implementation:**
  - **Reuse verbatim (no changes needed):** `rejectIfInsufficientProjectRoleForReveal` (AC-2), `validateFieldKey`/`fieldMetaForResponse` (AC-4), `claimSingleUseView` (AC-13), `revokeShare`/`findShareInScope` (AC-6), `autoRevokeSharesForDeactivatedUser` (AC-14), `writeHumanAuditEntryOrFailClosed` + the `security: { writeAuditEvent: false }` opt-out pattern (AC-11), `revealCurrentValue` (the underlying value-fetch, already generic over `fieldKey`), `constantTimeHexEqual` (AC-17), the `AuditEvent.CREDENTIAL_SHARE_*` constants (AC-11), `findBlockingShareIds`/archival guard (AC-20).
  - **New sibling implementation needed (fundamentally different auth model, cannot share the session-bound code path):** `findShareByToken`/`revealShare` in `service.ts` are written around `sessionUserId` as a required parameter (used for the AC-7-of-17.1 identity-match check) — the external path has no `sessionUserId` at all, so this story needs its **own** `findExternalShareByTokenHash`/`revealExternalShare` functions rather than making `sessionUserId` optional on the existing ones (making it optional would silently weaken 17.1's session-identity check if a future edit ever forgot to pass it — a foot-gun worth avoiding by keeping the two code paths structurally distinct, even though they share most of their internals via the smaller reused primitives above). The two new functions should still delegate to the same shared primitives (`claimSingleUseView`, `validateFieldKey`, etc.) rather than re-deriving that logic.
  - **New, no 17.1 analogue at all:** the step-up re-auth helper (Task 2), the pending-external-share cap check (Task 3.1), the admin-notification-on-first-view wiring (Task 4.2) — 17.1 notified the *recipient*, this story notifies *admins*, a different dispatcher function (`dispatchOrgAdminNotification` vs. `dispatchDirectUserNotification`) entirely.

- **RLS exception — cite both precedents, understand why the mechanical one is the closer fit:** The epic architecture note (`sprint-change-proposal-2026-07-24.md` §4.3, and `architecture.md` §"RLS exception tables — `sessions` and `refresh_tokens`", lines ~1182-1191) describes the *conceptual* category this needs — an unauthenticated-bearer-token path around normal `org_id`-scoped RLS. But `sessions`/`refresh_tokens` are tables that **have no `org_id` column at all** and are wholesale-excluded from RLS coverage via `EXCLUDED_TABLES` in `packages/db/src/check-rls-coverage.ts` — that shape doesn't fit here, because `credential_shares` **does** have `org_id` and **does** have a working RLS policy that 17.1's session-authenticated path already depends on; excluding the whole table from RLS coverage would remove protection for 17.1's rows too. The mechanically-correct precedent, already implemented and tested in this codebase, is **Story 6.3's public status page** (`apps/api/src/modules/monitoring/public-status-page-routes.ts` + `status-page-service.ts#findStatusPageByTokenHash`): a `requireAuth: false` route whose *first* DB touch is a single indexed point-lookup by hashed token on the **admin connection** (`getAdminDb()`, `apps/api/src/lib/db.ts`) — because the org is genuinely unknown before that lookup resolves — followed immediately by re-scoping to `withOrg(orgId, ...)` (`packages/db/src/index.ts`) for every subsequent query in the request. Follow that pattern exactly; do not add `credential_shares` to `EXCLUDED_TABLES`.
- **`requireAuth: false` mechanism:** confirmed present and already used by `publicStatusPageRoutes` — `apps/api/src/lib/secure-route.ts` reads `security.requireAuth !== false` to decide whether to attach `fastify.authenticate` as a `preHandler`; passing `requireAuth: false` skips it. `requireOrgScope` also defaults off when `requireAuth` is false (line ~296) — confirm this composes correctly with the manual `withOrg` re-scoping described above rather than fighting it.
- **Step-up re-auth has no existing precedent in this codebase — this story creates the first one.** Confirmed by search: no `stepUp`/`reauth`/`recentAuth` pattern exists anywhere in `apps/api/src`. Build the minimal version described in AC-3 (stateless, single-request password-or-TOTP re-verification) rather than a stateful "elevated session" mechanism — the latter is a meaningfully larger feature (new token type, new expiry, new revocation surface) that nothing in FR122-125 or the security review actually asks for; the security review's own wording ("requires the sharer to step up (re-auth: password or MFA)") is satisfied by a per-request re-check.
- **`SHARE_DEFAULT_TTL_MS`/`SHARE_MAX_TTL_MS` (17.1) are for member shares only — do not reuse those constants for external shares.** Define new `EXTERNAL_SHARE_DEFAULT_TTL_MS` (1h) / `EXTERNAL_SHARE_MAX_TTL_MS` (72h) constants in the same file (`apps/api/src/modules/credential-shares/schema.ts`), clearly named to avoid a future maintainer accidentally wiring the wrong constant into the wrong path.
- **PR #251 — the concrete lesson to not repeat (Previous Story Intelligence, restated for emphasis since two of its four findings are directly reproducible in this story's new code):**
  1. *Revoke auth-bypass ordering bug*: the original 17.1 revoke handler mutated the share to `revoked` **before** checking sharer/admin authorization, so a denied caller's request still revoked the share server-side (the route runs inside a transaction that commits on any non-throwing return) while only returning a 403 to the caller. Fixed by checking authorization **before** calling `revokeShare()`. This story reuses the already-fixed `revokeShare`/route ordering (Task 5.1) — but if the dev agent writes **any** new mutate-then-check code path for the external flow (there shouldn't be one, per the reuse map above), apply the same auth-before-mutate discipline.
  2. *Single-use-burn-on-missing-field ordering bug*: the original `revealShare` called the atomic single-use claim **before** checking the shared field still existed, silently consuming the token (and inflating `view_count`) with **zero** `CREDENTIAL_SHARE_VIEWED` audit entry when the field had been renamed/removed since creation. Fixed by reordering `revealCurrentValue`'s field-existence check **before** `claimSingleUseView`. The new `revealExternalShare` function this story writes (see reuse map) must preserve that same ordering from its first commit — field-check, *then* claim — not rediscover the bug in a parallel code path.
  3. *Referrer-Policy page-vs-API gap*: restated fully in AC-10 above; Task 7.2 exists specifically to front-load this fix rather than let it surface in review again.
  4. *Metadata GET never lazily expired the share*: `findShareByToken` originally reported a past-due share as `active` on the metadata GET (only the reveal-step applied the lazy expiry transition). The new `findExternalShareByTokenHash` must apply the same lazy `active`/`pending` → `expired` transition on the metadata GET, not only on reveal — write this in from the start rather than as a follow-up patch.
- **`credential_shares.status` enum note:** the security review's §1.1 design doc used `pending` as the initial status name; 17.1's actual shipped migration uses `active` as the initial status (confirmed by reading `packages/db/src/schema/credential-shares.ts`'s `statusCheck` constraint: `'active','viewed','revoked','expired','superseded'` — no `'pending'` value exists in the real schema). This story's ACs above use "active" (the real column value) and mention "pending" only where quoting the security-review doc's own vocabulary for a *concept* (e.g. "concurrent pending external shares" in AC-16 means "shares with real status `active`, not yet viewed/expired/revoked") — do not attempt to add a literal `pending` status value; there isn't one, and 17.1 already established `active` as the correct term for "not yet resolved."
- **`INVITATION_TOKEN_HMAC_SECRET` reuse (17.1's `generateShareToken`/`hashShareToken`) applies unchanged to external tokens too** — no new secret needed, same domain-separation prefix (`credential_share:`) already covers both recipient types since the prefix has nothing to do with recipient type.
- **`prd.md`/`epics.md` still do not contain Epic 17 / FR122-125 text**, re-verified at this story's creation time (grep against both files returned no matches) — same gap 17.1 flagged and left out of scope; still out of scope here unless it blocks review.
- **ADR — link delivery is manual, not auto-emailed (confirmed via Architecture Decision Records elicitation, not assumed):** `sprint-change-proposal-2026-07-24.md` §4.4 UX spec explicitly describes the created link as "generated link (masked, copy-once affordance for external)" — the product does **not** send an email to `recipientEmail` on Morgan's behalf; `recipientEmail` exists to identify/label the share (for the Shares-tab listing and audit trail) and to know who to notify-in-spirit, not as a delivery address the system dispatches to.
