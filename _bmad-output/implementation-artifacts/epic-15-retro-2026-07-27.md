### Step 3: What Went Well

- **Explicit rejection of the obvious shortcut, twice.** `15-1`'s ADR rejected Paraglide's own
  tutorial-default URL-prefixed routing in favor of a cookie-based strategy, specifically because
  URL-prefixing would conflict with the "no reload" AC. `15-2`'s Task 2.4 explicitly declined to
  generalize `updateOrgDormancyColumn`, to avoid risking regression in two already-`done` routes for a
  ~15-line savings. Both are documented, reasoned "no" calls, not just implementation notes.
- **Regression coverage anticipated real risks, not just AC boxes.** `15-1`'s test suite includes a
  credential literally named `{count} servers` (guarding against ICU MessageFormat injection via
  user-generated content) and an audit-export locale-invariance test triggered directly via the API
  with no `Accept-Language` header — both edge cases that would be easy to skip and weren't.
  (Dana (QA Engineer))
- **Live-Chrome verification earned its keep.** `15-1`'s `ORIGIN`/CSRF bug is the first case in this
  project where manual browser verification caught something the automated suite structurally
  couldn't — the first SvelteKit form action anywhere in the app, so no existing test exercised that
  code path. (Elena (Junior Dev))
- **Hot-path risk was explicitly flagged, not discovered the hard way.** `15-2`'s own Pre-Mortem
  Analysis called out that `organizations.default_locale` is read on *every registration* — unlike
  `15-1`'s passive settings-page column — and added Task 5.3 specifically to force an explicit
  migrate-before-deploy confirmation rather than assuming it. (Charlie (Senior Dev))

## Gaps, Inconsistencies & Risks Audit

*(requested focus: incongruencies, inconsistencies, gaps, technical debt, and risks)*

### 1. [Medium] Three near-identical settings-PATCH handlers in `organization-settings-routes.ts` — duplication now past the 2-instance threshold

`updateOrgDormancyColumn` (shared by the machine-key and user-dormancy routes) and the new
`updateOrgDefaultLocaleColumn` (added by `15-2`) both implement the same shape: params → body-parse →
cross-org-404 guard → read-previous-value → `UPDATE ... RETURNING` → inline fail-closed audit write.
`15-2`'s own Task 2.4 documents a deliberate, reasoned decision *not* to generalize the shared helper,
specifically to avoid risking regression in two already-`done` routes for a small line-count saving.
Each individual decision was sound, but the codebase now has three copies of the same shape — past the
"2+ instances" duplication threshold this audit treats as worth naming, even though forcing a refactor
now would re-open the exact regression risk `15-2` correctly declined to take on.
**Resolution:** Tracked as debt, not urgent. A fourth org-settings route (the next one added) should be
the trigger to actually extract the common shape — don't force it retroactively on three routes two of
which are already stable in production.

### 2. [Low] `GET /me` response schema still hardcodes the locale enum instead of deriving it from `SUPPORTED_LOCALES`

`apps/api/src/modules/users/routes.ts`'s `usersMeResponseSchema` still has `locale: z.enum(['en', 'es'])`
literally duplicating `SUPPORTED_LOCALES` rather than importing it — the exact item `15-1`'s Dev Agent
Record and `sprint-status.yaml` already flagged as an accepted low-severity follow-up. Confirmed not
touched incidentally by `15-2` (whose own new schema, `UserLocaleBodySchema`/`ResponseSchema`, correctly
uses `z.enum(SUPPORTED_LOCALES)`).
**Resolution:** Accepted as-is (already documented, low blast-radius); fold into the next
locale-touching story rather than opening a dedicated one.

### 3. [Low] `es.json` missing one translation key present in `en.json` — intended behavior, not a regression

`apps/web/messages/es.json` has 12 keys vs. `en.json`'s 13 — `settings_language_save_success` is absent
from the Spanish file. This is the exact, pre-documented per-string-fallback case `15-1`'s own Dev Notes
("Demo/seed-translation risk") called out as correct-but-can-look-like-a-bug: Paraglide falls back to
English for the missing key, and the incremental-translation coverage note (`settings_language_coverage_note`)
is present and correctly worded in both locale files.
**Resolution:** Accepted as-is per `15-1`'s own documented rationale; translate the missing string
opportunistically if/when anyone notices the English save-success toast, not worth its own action item.
