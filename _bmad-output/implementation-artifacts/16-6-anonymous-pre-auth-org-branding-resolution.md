# Story 16.6: Anonymous Pre-Auth Org Branding Resolution

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a returning anonymous visitor to a pre-auth page (login, registration, or invitation-accept),
I want the page to show my organization's branding immediately on first paint, without having to retype my email again,
so that the pre-auth experience feels consistently on-brand across visits instead of always flashing the generic base theme until I re-enter my email.

### Persona journey stub

**Alex (returning Acme Corp employee, day 2+):**
1. Yesterday, Alex typed `alex@acme.com` on the login screen. `acme.com` resolves via `org_sso_domains` (Story 14.4) to Acme Corp, which has a configured, currently-valid `default_theme_name = "acme-brand"` (Story 16.4). The login screen applied `acme-brand`'s branding, exactly as Story 16.4 built. This story additionally caches that resolution (`{ name: "acme-brand", css: "..." }`) in the browser's `localStorage`, keyed to nothing more than "the last theme this browser successfully resolved" — no org id, no email, no account link.
2. Today, Alex closes the tab and reopens `https://vault.example.com/login` fresh (a real navigation, not a client-side `goto()`). Before Alex types anything — before Step A's email field even exists on screen — the login page reads the cached entry, finds it not expired (within its 7-day bound), and applies `acme-brand`'s branding immediately on mount. Alex sees Acme Corp's colors and logo from the very first frame.
3. Alex types their email as usual and logs in normally — this story changes nothing about the actual authentication flow, only what's painted before that flow starts.

**Jordan (different employee, shared kiosk laptop):**
1. Jordan uses a shared onboarding kiosk laptop that a previous new-hire, Priya from a different org (`Startup Inc`, theme `startup-theme`), used yesterday to accept their invitation.
2. Jordan opens the login page on the same laptop/browser profile. The cached entry from Priya's visit (`startup-theme`) is applied on first paint — Jordan briefly sees `Startup Inc`'s branding, not their own org's, until they type their own email.
3. The moment Jordan types `jordan@acme.com` and the existing domain-lookup resolves (Story 14.4/16.4's unchanged mechanism), Acme Corp's `acme-brand` supersedes the stale cached value immediately — the cache write-through updates to `acme-brand` for the *next* visitor on this shared machine. This cross-visitor bleed on shared devices is a known, accepted, self-correcting trade-off (see Dev Notes "Shared-device disclosure is bounded and self-correcting") — the cached value carries no secret or account-linked data, only a non-sensitive, org-admin-chosen theme name/CSS already publicly resolvable via the exact same domain-lookup call any visitor could make anyway.

**Expected UI outcome:** A previously-resolved, still-valid org theme is applied on the very first paint of `/login`, `/register`, and `/invitations/accept`, superseding the base theme before any user input — closing the "before any email is typed" gap Story 16.4's Out of Scope section named as the largest deviation from the PRD's Amara narrative, for the common returning-visitor case, without inventing any new org-identification primitive.

## Acceptance Criteria

> No `epics.md` entry exists for this story — it was created directly from `epic-16-retro-2026-07-29.md` Finding 1 (High, `[Treated as REPEAT 2x]`) and the `sprint-status.yaml` scope note (see References). Story 16.4's Out of Scope section named "zero-input pre-auth branding (before any email is typed)" as "the single largest gap versus the PRD's Amara narrative" and explicitly deferred it as needing "a general-purpose pre-auth org-resolution mechanism" — this story is that follow-up, scoped to the minimal design that closes the gap without building the heavier, explicitly-rejected primitive (see Dev Notes "Design rationale" for the four alternatives considered and why the chosen design won). Every AC below includes a concrete happy-path example and at least one concrete edge/failure-case example, per this story's authoring mandate.

### AC-1: a successful pre-auth theme resolution is cached client-side for future visits

**Given** any of the three existing pre-auth call sites (`LoginForm`'s Step A submission, `RegisterForm`'s blur/mount resolution, `invitations/accept`'s peek-triggered resolution — all built by Stories 16.4/16.5 and all already routed through the shared `resolvePreAuthTheme()` helper in `apps/web/src/lib/components/auth/form-model.ts`) resolves a **non-null** `{ name, css }` theme pair, **when** that resolution completes, **then** the pair is written to `localStorage` under a single, versioned key (`pv:preAuthTheme:v1`) as `{ name, css, savedAt: <epoch ms> }`, overwriting any previously cached value.

- **Positive:** Alex types `alex@acme.com` on `/login`; the domain-lookup resolves `{ name: "acme-brand", css: "..." }`. `localStorage.getItem('pv:preAuthTheme:v1')` now returns `{"name":"acme-brand","css":"...","savedAt":1735689600000}` (or the current implementation's exact timestamp).
- **Positive — write-through from any of the three call sites:** The same write happens identically whether the resolution came from `LoginForm`, `RegisterForm` (Story 16.5 AC-1/AC-2), or `invitations/accept` (Story 16.5 AC-3) — because all three already funnel through the one shared `resolvePreAuthTheme()` helper, this story adds the persistence call in exactly one place (that helper), not three.
- **Edge/failure — a miss (`{ name: null, css: null }`) does NOT write to the cache:** Jordan types `jordan@startupinc.example` (no `org_sso_domains` mapping). The resolution is `{ name: null, css: null }` — the existing cached entry (if any) is left untouched. See AC-3 for the full rationale; a miss must never destroy a still-potentially-valid cached value from a different, earlier resolution.
- **Edge/failure — `localStorage` unavailable (private/incognito mode with storage disabled, or quota exceeded):** The write is wrapped in its own `try`/`catch`; a thrown `DOMException` is swallowed silently and never surfaces to the user or blocks the theme resolution itself from applying via the existing in-memory rune (`setPreAuthTheme()`, unchanged). Add a test simulating `localStorage.setItem` throwing and asserting the resolution still completes normally.
- **Edge — CSS payload size:** Reuses the exact same compile-time-size-bounded CSS Story 16.4's Pre-Mortem #1 already confirmed capped — no new size concern introduced by additionally persisting it to `localStorage` (well within typical per-origin `localStorage` quotas of several MB).

### AC-2: pre-auth pages apply the cached theme optimistically on first paint, before any lookup

**Given** a fresh (non-SPA, full-navigation) load of `(auth)/+layout.svelte` — the shared layout wrapping `/login`, `/register`, and `/invitations/accept` (Stories 16.4/16.5) — **when** the layout mounts and the in-memory `preAuthThemeName`/`preAuthThemeCss` runes are still at their default `null`/`null` (i.e., no page-level resolution has already run this load), **then** the layout reads the cached entry and, if present and not expired (AC-4), applies it via a new `seedPreAuthThemeFromCache()` call — the login/register/invitations pages render branded from their very first frame, without waiting for any domain-lookup round trip.

- **Positive:** Alex reloads `/login` fresh a day after their last visit. `(auth)/+layout.svelte`'s `onMount` calls `seedPreAuthThemeFromCache()`, which reads the valid, unexpired cached `acme-brand` entry and calls the existing `setPreAuthTheme("acme-brand", "<cached css>")` setter — `data-theme="acme-brand"` and the injected `<style>` are present on the very first client-rendered frame (there is no SSR seed for this layout, per Story 16.4's own documented `(app)` vs `(auth)` asymmetry, so "first paint" here means "first client-side render," same bar 16.4/16.5 already accept for this layout).
- **Positive — superseded by a fresh resolution:** After the cache-seeded `acme-brand` applies, Alex still types their email and submits; the resulting fresh domain-lookup resolution (whatever it resolves to, including re-confirming `acme-brand`) calls `setPreAuthTheme()` again via the existing, unmodified 16.4/16.5 call sites — this always wins over the cache-seeded value, since it runs strictly later in the same page's lifecycle. No special-casing needed: the last `setPreAuthTheme()` call always wins, exactly as it already does today between multiple lookups.
- **Edge/failure — no cached entry exists (first-ever visit to this browser):** `seedPreAuthThemeFromCache()` is a no-op; the page renders the base theme on first paint, identical to today's pre-story behavior. This is the expected common case for a brand-new visitor and is not a regression.
- **Edge/failure — cached entry is malformed or from an incompatible future/past schema version:** `JSON.parse` throws, or the parsed shape is missing `name`/`css`/`savedAt` — treat identically to "no cached entry": silently ignore (do not throw, do not apply a partial/broken theme), and do not attempt to repair or migrate the malformed entry (the versioned key name, `v1`, is the intended forward-compatibility mechanism — a future format change ships as `v2` and simply never reads `v1` entries, which age out naturally via AC-4's TTL).
- **Edge — a client-side `goto()` navigation between `/login` and `/register` (no full reload):** The in-memory rune already carries whatever theme was last resolved/seeded (Story 16.4/16.5's existing SPA-persistence behavior, unchanged) — `seedPreAuthThemeFromCache()` only runs once, on the layout's initial mount for a given full navigation, not on every internal route change within the `(auth)` group. No double-seeding, no flicker between pages in the same SPA session.
- **Edge/security — a tampered or maliciously-written cache entry (browser extension, a one-time unrelated XSS bug elsewhere, or local/physical access writing directly to `localStorage`):** `localStorage` is a plain, unauthenticated, script-writable bag with no origin-side integrity guarantee — the CSS in a cached entry was validated (Story 16.1's canonical token registry / per-type CSS grammar, `validateAndCompileTokens` in `apps/api/src/modules/theming/service.ts`) at the moment it was *first compiled server-side*, but nothing re-checks it once it has passed through `localStorage`, where any other script running on the same origin could have overwritten it. **Correction from this elicitation round's first draft:** Story 16.1's full validator is a private, server-only function with Node-only dependencies (filesystem reads, the SSRF-checked asset fetcher, DB access) — it cannot be imported into `apps/web` as originally proposed, and refactoring it into a shared, isomorphic module is a larger extraction than this story's stated scope justifies. Instead, `seedPreAuthThemeFromCache()` runs a new, deliberately narrower, client-safe structural sanity check (`isSafeCachedThemeCss()`, a new small pure function in `apps/web`, NOT a reuse of the server validator) before calling `setPreAuthTheme()`: reject the cached CSS string if it contains any of a short deny-list of unambiguously-dangerous constructs (`expression(`, `@import`, `javascript:`, `<script`, `behavior:`, or a `url(` referencing anything other than `data:` or the same known-safe asset-CDN origin pattern Story 16.1 already established). This is intentionally a defense-in-depth backstop, not a re-validation guarantee equivalent to the server's full grammar — the authoritative validation remains the existing server-side compile step (unchanged); this client-side check only bounds the blast radius of a *already-compromised* browser replaying tampered `localStorage` content. If the check fails, treat identically to a malformed entry (AC-2's prior bullet): silently ignore and remove the key, fall open to the base theme. Add a test asserting a cached entry containing each deny-listed construct is ignored and removed exactly like a malformed-shape entry.

### AC-3: the cache is never actively cleared on a miss — only ever superseded by a newer resolution

**Given** the cache represents "the last theme this browser successfully resolved" rather than "the theme for the domain most recently attempted," **when** any subsequent lookup misses (resolves `{ name: null, css: null }`) or fails, **then** the existing cached entry is left untouched in `localStorage` — it is not deleted, nulled, or overwritten with an empty value.

- **Positive:** A returning visitor with a valid `acme-brand` cached entry types a typo'd email that doesn't resolve to any org. The in-memory rune correctly falls open to base theme for *this page render* (existing 16.4/16.5 fail-open behavior, unchanged), but the cached `acme-brand` entry survives in `localStorage` for the *next* fresh page load, where it will again be seeded optimistically.
- **Rationale (why this is correct, not a bug):** if a miss cleared the cache, a single mistyped email or a one-off visit to a colleague's unrelated-org email field would permanently erase the returning-visitor benefit this story exists to provide, for no correctness gain (a miss says nothing about whether the *previous* cached resolution is still valid — that's AC-4's job, via TTL, and any subsequent *hit* already overwrites it per AC-1).
- **Edge/failure — explicit logout:** Logging out does not clear the pre-auth theme cache (see AC-8) — it is unauthenticated, account-independent state; there is nothing about a logout event that implies the cached branding is now wrong.
- **Edge — the only way the cache is ever removed before its TTL:** overwritten by a newer successful hit (AC-1), or expired past its TTL bound (AC-4). There is no explicit "clear branding cache" user action in this story's scope (see Out of Scope).

### AC-4: the cache respects a bounded TTL and self-expires

**Given** a cached entry's `savedAt` timestamp, **when** `seedPreAuthThemeFromCache()` reads it, **then** an entry older than 7 days is treated as expired — ignored (not applied) and proactively removed from `localStorage` rather than left to be silently ignored forever.

- **Positive:** A cached entry with `savedAt` 3 days ago is applied normally (within the 7-day bound).
- **Edge/failure — a cached entry with `savedAt` 10 days ago:** Ignored; `localStorage.removeItem('pv:preAuthTheme:v1')` runs as part of the same read, so a subsequent read doesn't repeat the expiry check against stale data every load. Base theme renders on first paint until a fresh resolution re-populates the cache.
- **Edge — why 7 days, not 30 (as considered and rejected):** A shorter bound (7 days) caps the "shared-device shows a stale prior visitor's branding" window (AC-5's accepted trade-off) more tightly than a longer one would, while still covering the realistic "logs in most weekdays" returning-user case this story targets. A 30-day bound was considered and rejected as unnecessarily widening the shared-device disclosure window for marginal added convenience — 7 days is a deliberate, documented choice, not an arbitrary default.
- **Edge — clock skew / a `savedAt` timestamp in the future (clock changed on the client):** Treated as **not expired** (a future `savedAt` is, by construction, less than 7 days old under any correct comparison — `Date.now() - savedAt < sevenDaysMs` still holds even for a negative difference) — no special-casing needed; document this as intentional so a reviewer doesn't add unneeded clock-skew handling.

### AC-5: shared-device disclosure is bounded and self-correcting (accepted trade-off, not a defect)

**Given** `localStorage` is scoped to the browser/device, not to any authenticated identity, **when** a shared device (kiosk, shared workstation) is used by visitors from different organizations in sequence, **then** each visitor's first paint may show the *previous* visitor's cached org branding until their own email resolves a fresh value — an explicitly accepted, cosmetic-only, non-sensitive, self-correcting trade-off.

- **Positive/expected — self-correction:** As soon as any visitor's own email resolves (hit or miss), the in-memory rune reflects their own resolution immediately for their own session (AC-1/AC-3), and a hit also overwrites the shared cache for whoever uses the device next.
- **Not a security or privacy issue — confirm no new information class:** The cached `{ name, css }` pair is the identical, already-non-sensitive, org-admin-chosen display data Story 16.4's Red Team round (epic-16-retro-2026-07-29.md context) already accepted as publicly resolvable by any anonymous caller of `POST /domain-lookup` for any domain they choose to try — this story only changes *when* that already-obtainable data is displayed (proactively, from a prior visit, vs. reactively, after typing an email), not *what* is disclosed or *to whom*. No account identifier, email, org id, or any secret ever enters `localStorage` — only a theme name string and its compiled, non-secret CSS.
- **Edge/failure — a security-conscious org objects to even cosmetic cross-visitor bleed on shared devices in their own environment:** No per-org opt-out is built in this story (see Out of Scope) — the mitigation available today is the same one available for any browser-persisted state: clearing browser storage, or using a private/incognito window (which Story AC-1's `localStorage`-unavailable path already falls open from gracefully). If this proves to be a real operational pain point, the correct escalation is a small follow-up (e.g. a `Cache-Control`-style admin toggle, or gating the feature off by default in a locked-down deployment profile) — not a silent scope expansion here.
- **Edge — this is strictly less exposure than a session cookie would have been:** a cookie-based design (considered and rejected, see Dev Notes "Design rationale") would auto-attach to every request including ones the page's own JS never explicitly reads, and would need explicit `SameSite`/`Secure` reasoning; a `localStorage` entry is inert until this story's own code explicitly reads it, with no automatic network transmission at all.

### AC-7: audit behaviour

**Given** this story's only new logic is client-side reads/writes to `localStorage` (never a server-side write of any kind), **when** the cache is written, read, applied, or expired, **then** no audit entry is written anywhere — identical reasoning to Story 16.4 AC-5/16.5 AC-6's "read-only theme resolution is never audited" convention, extended to a client-side cache of that same read-only data.

- **Positive:** Every audit entry this story's flows can produce (registration, invitation acceptance, login) is identical to pre-story — no new audit event type, no new audit call site.
- **Edge — do not add a "cache write" telemetry event "for completeness":** Per-page-load client-side cache writes at request-adjacent frequency would be pure noise, identical reasoning to every sibling AC in this epic that explicitly rejects logging read-only, high-frequency operations.

### AC-8: auth/session lifecycle

**Given** the pre-auth theme cache is browser-scoped `localStorage` state entirely independent of any session, cookie, or JWT, **when** a user logs in, logs out, or their session expires, **then** none of those events read, write, or clear the cache — it persists across authentication state changes exactly as it persists across page reloads (bounded only by AC-4's TTL).

- **Positive:** Alex logs in successfully (moves to an authenticated `(app)` session). The pre-auth cache is untouched — irrelevant to the authenticated experience, which has its own, unrelated, already-shipped org-default-theme resolution (Story 16.4 AC-2, `(app)`-layout-scoped, SSR-seeded, never client-cached).
- **Edge — logout and return to `/login`:** The same cached entry (if not yet expired) is seeded again on the next `/login` visit — logout has no special-case interaction with this story's cache at all, by design (there is nothing account-specific in the cached data to invalidate on logout).
- **Edge — no MFA gate anywhere in this story:** Every read/write in this story is unauthenticated, client-side-only state manipulation — no session, no auth header, no MFA posture exists to reason about, unlike Story 16.4's AC-1 write path (which is a real authenticated, MFA-gated PATCH). This story introduces no new authenticated surface at all.

### AC-9: concurrent access

**Given** `localStorage` is shared across all tabs/windows of the same browser profile for the same origin, **when** two tabs are open simultaneously (e.g. one on `/login`, one on `/register`) and both resolve different themes around the same time, **then** the browser's own `localStorage` last-write-wins semantics apply — no coordination, locking, or cross-tab messaging is built in this story.

- **Positive:** Tab A resolves `acme-brand` and writes the cache; Tab B (a different visitor scenario, same physical browser) resolves `startup-theme` moments later and overwrites the cache. Whichever tab is reloaded next seeds from whichever value was written last — this is expected, harmless, cosmetic-only behavior, identical in kind to Story 16.4 AC-7's already-accepted "last commit wins, no locking" reasoning for the server-side PATCH route, now applied to a client-side cache instead.
- **Edge — no `storage` event listener added:** This story does not make an already-open tab reactively repaint if *another* tab changes the cache mid-session (no `window.addEventListener('storage', ...)` wiring) — each tab only ever reads the cache once, at its own layout's initial mount (AC-2). Adding live cross-tab reactivity would be a new, unrequested feature; explicitly out of scope (see Out of Scope), mirroring Story 16.2 AC-6's own "no live cross-tab push" precedent for the authenticated theme-selection feature.

### AC-10: rate limits

**Given** this story adds no new network call of any kind — it only persists and replays data already obtained by Story 16.4/16.5's existing, already-rate-limited `POST /domain-lookup` call sites, **when** reasoning about rate-limit impact, **then** there is none: zero new requests are introduced, and the existing `{ max: 20, timeWindowMs: 15 * 60 * 1000 }` budget (Story 14.4 AC-9, unchanged and unmoved by 16.4/16.5) is entirely unaffected.

- **Positive:** A returning visitor whose branding is seeded entirely from cache issues **zero** domain-lookup calls until they actually type an email — this story, if anything, *reduces* the practical call volume for a repeat visitor's first paint, not increases it.
- **Edge — no new rate-limit key needed:** Confirmed no client-side "cache read" operation ever reaches the network layer at all; there is nothing to rate-limit.

- **Positive/Edge:** No test needed beyond confirming no new `req.log`/`operationalLog()` call exists anywhere in this story's diff (a code-review-time check, not an automated assertion) — this story's entire diff is `apps/web/`; there should be zero `apps/api/` changes to check in the first place, confirmed explicitly rather than assumed (same discipline Story 16.5 Task 3.3 established).

## Out of Scope (explicit — do not scope-creep)

- **A general-purpose, org-admin-configured email-domain-to-org resolution mechanism, org-vanity-URL/slug, or subdomain-based tenancy.** These were the actual candidate designs considered for "true" zero-input, first-ever-visit branding (a visitor who has *never* visited this browser before, and never will type a resolvable email) — all rejected as materially larger scope than this Medium-High/High-treated retro finding justifies (new admin-configured mapping, new public lookup surface, or new routing/reverse-proxy infrastructure respectively). See Dev Notes "Design rationale" for the full comparison. This story closes the gap for the **returning-browser** case only, which the retro's own framing and this story's persona journey treat as the realistic, common instance of "before any email is typed."
- **A true first-ever-visit, any-browser, zero-prior-state branding mechanism.** Structurally unsolvable without one of the heavier primitives above — still an open gap after this story, same as Story 16.4 already documented and this story does not claim to fully close. If a reviewer judges the remaining gap unacceptable, the correct escalation is a dedicated follow-up story building one of the explicitly-rejected heavier primitives (e.g. org vanity URLs) — not a silent expansion of this story.
- **Live cross-tab cache invalidation/reactivity (a `storage` event listener).** See AC-9 — each tab reads the cache once, at mount; no live push between open tabs.
- **A per-org or per-deployment opt-out toggle for this caching behavior.** See AC-5 — no admin control is added to disable client-side caching for privacy-sensitive deployments in this story; noted as a plausible future escalation if it becomes a real operational complaint, not built speculatively here.
- **Any change to `POST /domain-lookup`'s backend implementation, request/response schema, or rate-limit configuration.** Identical non-goal to Story 16.5 — this story is client-side-only, reusing the exact response shape Story 16.4 built, unmodified.
- **Persisting the cache anywhere other than `localStorage`** (e.g. a first-party cookie, IndexedDB, or a server-side session). `localStorage` was the deliberately chosen mechanism — see Dev Notes "Design rationale" for why a cookie was considered and rejected.
- **Caching or seeding the *authenticated* `(app)` layout's org-default-theme resolution (Story 16.4 AC-2).** That path is already SSR-resolved fresh on every load from the database and is explicitly unrelated to this story's unauthenticated, client-only cache — no change to it.

### Design rationale — four alternatives considered for "branding before any email is typed"

This is the design work `sprint-status.yaml`'s scope note asked this story to do, starting from Story 16.4's own "Alternative B" reasoning rather than from scratch.

1. **A dedicated public "org-by-domain" or "org-by-slug" lookup endpoint, independent of `org_sso_domains`.** This is Story 16.4's own rejected "Alternative B" (*"resolve theme client-side from a public, unauthenticated `GET /organizations/by-domain/:domain` style endpoint... a new general-purpose pre-auth org-resolution primitive — exactly the thing 'Out of Scope' already rules out... would also require a new rate-limit budget"*). Still rejected here for the identical reason, now generalized: any design that requires the server to accept some new client-supplied identifying token (a slug, a subdomain, a bookmarked org-specific URL) and resolve it to an org is the heavier "general-purpose pre-auth org-resolution mechanism" both this story's scope note and 16.4's Out of Scope explicitly deferred as future, larger-scoped work — not because it's technically hard, but because it requires new admin-facing configuration (an org must register/claim a slug or subdomain) that is a materially larger, differently-shaped feature than this High-treated-but-still-single-story retro finding justifies.
2. **Subdomain-based / custom-domain-based tenancy** (e.g. `acme.vault.example.com`). Rejected: `architecture.md` confirms self-hosted deployments run "single or multi-org" on one instance/hostname (line ~495) — there is no existing per-org hostname/subdomain routing anywhere in this codebase, and building one would mean new reverse-proxy/host-header-parsing infrastructure, a DNS/TLS story of its own, and a mechanism that doesn't even apply to the common self-hosted single-hostname deployment this product's OSS tier targets (per `prd.md`'s deployment model). Far outside this story's scope.
3. **A first-party cookie carrying the last-resolved org/theme, set by the server on every domain-lookup response.** Considered as the most direct analog to "remember the last thing this browser learned." Rejected in favor of `localStorage` for three concrete reasons: (a) a cookie auto-attaches to *every* subsequent request to the origin, including ones that have nothing to do with theming, silently growing every request's header size for a purely cosmetic feature; (b) it invites `SameSite`/`Secure`/`HttpOnly` design questions with no real benefit here (the value is non-secret and only ever needs to be read by this story's own client-side JS, never by the server) — using `localStorage` sidesteps that entire class of question by construction, since it is never transmitted automatically at all; (c) cookies are commonly scoped/cleared by different browser privacy heuristics (e.g. more aggressive default cookie-clearing than `localStorage` in some browsers' tracking-protection modes) that would make this story's already-modest returning-visitor benefit less reliable in practice.
4. **`localStorage`-cached last-resolved theme, applied optimistically on layout mount, write-through from the existing domain-lookup call sites (chosen).** The minimal design that closes the "before any email is typed" gap for the realistic, common **returning-browser** case (the persona journey's actual framing) without building any new backend primitive, new admin configuration, or new information-disclosure class beyond what Story 16.4's Red Team round already accepted as non-sensitive. It deliberately does **not** claim to solve the harder, structurally-different "any browser, ever, first visit" case — that remains an open, named gap (see Out of Scope), exactly as Story 16.4 left it, but the realistic day-2-onward experience (the actual shape of daily active use, per `prd.md`'s own retention-oriented success metrics) is closed by this story.

### Pre-mortem — imagining this shipped and something went wrong

Three concrete failure scenarios considered, each resolved to either an explicit AC/task or a documented, accepted non-issue:

1. **A malicious or tampered cache entry silently re-applies on every visit.** Addressed by AC-2's new security edge case (added via this elicitation round) — `readPreAuthThemeCache()` runs `css` through a new client-safe structural sanity check (`isSafeCachedThemeCss()`) before it can ever reach `setPreAuthTheme()`, closing most of the "one XSS bug becomes a persistent one" amplification path. Note this is a deliberately narrower backstop than the server's full token-grammar validator (which cannot run client-side — see Task 1.3's Dev Notes correction), not an equivalent guarantee; it bounds blast radius rather than fully re-proving safety.
2. **Safari's Intelligent Tracking Prevention (or an equivalent browser privacy heuristic) evicts `localStorage` for the origin after a period of no top-level interaction, silently defeating the feature for some returning visitors.** This is not a bug to fix — it fails open exactly like AC-2's "no cached entry" case (base theme renders, identical to pre-story behavior), and this story never claims a guarantee stronger than "best-effort for browsers that retain first-party storage normally." No mitigation needed; noted here so a future investigator doesn't mistake reduced hit-rate in some browsers for a defect.
3. **A future developer, reasoning "this is auth-related state," adds a `localStorage.clear()` or a themed-cache clear call to the logout flow "to be safe."** AC-8 already states explicitly that logout must not touch this cache, with the rationale (no account-specific data to invalidate) — flagging here again because this is exactly the kind of "seems like the right thing to do" change that could silently regress the feature's entire value proposition without failing any test that doesn't specifically assert cache-survives-logout. Task 3.2's test list now includes this assertion explicitly.

**Occam's Razor check on the security addition above:** `isSafeCachedThemeCss()` is a short, static, dependency-free deny-list check, not a CSS parser or a reimplementation of the server's full token grammar — the minimal sufficient backstop for its actual job (bounding an already-compromised browser state), not a guarantee of equivalence with server-side validation. A heavier client-side parser was considered and rejected as unjustified scope for a defense-in-depth-only check.
