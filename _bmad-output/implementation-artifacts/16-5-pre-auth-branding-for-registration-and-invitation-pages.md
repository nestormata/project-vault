# Story 16.5: Pre-Auth Branding for Registration and Invitation Pages

Status: review

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a prospective org member visiting the registration or invitation-acceptance page,
I want to see my organization's branding (if it's already resolvable pre-auth, the same way the login screen resolves it),
so that the registration/invitation-accept experience feels consistent with the branded login screen instead of reverting to the generic base theme partway through the pre-auth journey.

### Persona journey stub

**Alex (invited, no account yet):**
1. Riley (Acme Corp admin) invites `alex@acme.com` to a project. Acme Corp has `org_sso_domains` mapping `acme.com` and a configured, currently-valid `default_theme_name = "acme-brand"` (Story 16.4's own precondition, unchanged here).
2. Alex clicks the invitation link, landing on `(auth)/invitations/accept?token=...`. The page's existing `peekInvitation()` call resolves `{ email: "alex@acme.com", accountExists: false, ... }`. Today (pre-story), the page briefly shows "Checking your invitation..." in the base theme, then redirects to `/register?invitationToken=...&email=alex%40acme.com` — also base theme, since `RegisterForm` never calls domain-lookup. After this story: the moment `peekInvitation()` resolves an email, the page fires the same `lookupSsoDomain()` call `LoginForm` already uses (Story 16.4), applying `acme-brand`'s branding via the shared `preAuthThemeName`/`preAuthThemeCss` runes — the redirect to `/register` carries that already-applied branding forward (client-side `goto()`, same rune state, no reload), so Alex never sees a mid-journey flash back to the base theme.
3. On `/register`, Alex's email is pre-filled and read-only (invitation flow). `RegisterForm` also independently resolves branding once on mount from its `prefillEmail` prop, so even a direct deep-link to `/register?invitationToken=...&email=...` (skipping the accept page) still shows `acme-brand`.
4. Alex sets a password and submits. Registration proceeds exactly as before — this story touches zero registration/invitation business logic, only the theme the surrounding page chrome shows while it happens.

**Jordan (self-registering, no invitation):**
1. Jordan navigates directly to `/register` (no invitation, no `email` query param). The email field starts empty; no branding is possible yet — same "cannot brand before an email exists" boundary Story 16.4 already established for the login screen's first render.
2. Jordan types `jordan@acme.com` and tabs/clicks away from the email field (blur). `RegisterForm` fires the same domain-lookup call, resolves Acme Corp's `acme-brand`, and the page picks up the branding reactively — Jordan finishes filling out the org-name/password fields under Acme Corp's theme, even though Jordan is about to create their *own* independent organization (not join Acme Corp) — see Dev Notes "Self-registration branding is cosmetic-only, not a trust signal" for why this is deliberately accepted.
3. Jordan then changes their mind and edits the email to `jordan@startupinc.example` (an org with no `org_sso_domains` mapping, the common case). Branding reverts to base the moment that lookup resolves (or immediately reverts to base once `RegisterForm` sees the current email no longer matches the email a theme was last resolved for, matching `LoginForm`'s own out-of-order-response race guard) — never a stale `acme-brand` lingering for the wrong email.

**Expected UI outcome:** `(auth)/register` and `(auth)/invitations/accept` show the same org branding `(auth)/login` already shows, resolved via the identical `POST /domain-lookup` mechanism, whenever an email on that page resolves to an org with a currently-valid default theme — with the same fail-open-to-base guarantees Story 16.4 already established.

## Acceptance Criteria

> No `epics.md` entry exists for this story — it was created directly from `epic-16-retro-2026-07-29.md` Finding 1 (High, REPEAT-2x-treated) and the `sprint-status.yaml` scope note (see References). Story 16.4's own Out of Scope section explicitly flagged `(auth)/register` and `(auth)/invitations/*` as "a plausible follow-up, not built here" — this story is that follow-up. Every AC below includes a concrete happy-path example and at least one concrete edge/failure-case example, per this story's authoring mandate.

### AC-1: `RegisterForm` resolves org branding for a free-typed email (self-registration flow)

**Given** a user on `/register` with no invitation token, **when** they type an email and blur the field, **then** `RegisterForm` calls `lookupSsoDomain()` (the exact same client function `LoginForm` already calls, Story 14.4/16.4 — no new API client function) and applies the resolved theme via `setPreAuthTheme()` (Story 16.4's shared rune), exactly mirroring `LoginForm`'s `submitEmailStep()` resolution/fail-open logic.

- **Positive:** Jordan types `jordan@acme.com`, blurs. `acme.com` resolves to Acme Corp with a valid `default_theme_name = "acme-brand"`. `setPreAuthTheme("acme-brand", "<compiled css>")` is called; `(auth)/+layout.svelte` (unmodified — Story 16.4 already wired it to read this shared rune) picks it up reactively, setting `data-theme="acme-brand"` and injecting the CSS.
- **Positive — invalid-email guard:** Jordan types `not-an-email` and blurs. No lookup fires — reuse the input's existing `type="email"`/HTML5 validity check (`event.target.checkValidity()` or equivalent) as a cheap client-side gate before spending a domain-lookup call on obviously-malformed input, avoiding wasted calls against the shared `{max:20, timeWindowMs:15min}` budget (AC-4). This mirrors no existing precedent verbatim (LoginForm has no such guard, since its Step A submission already implies a plausible email was typed) — a new, small, justified addition specific to this story's blur-triggered (not submit-triggered) call site.
- **Edge/failure — domain has no `org_sso_domains` mapping (the common case, e.g. `startupinc.example`):** `lookupSsoDomain()` resolves with `theme` absent/`null` (Story 16.4's existing miss-response shape, unchanged). `setPreAuthTheme(null, null)` is called; base theme shown. This is the expected, majority-case outcome for most self-registrations and is not an error state.
- **Edge/failure — out-of-order response race:** Jordan types `jordan@acme.com`, blurs (lookup A fires), then immediately edits to `jordan@other.example` and blurs again (lookup B fires) before A resolves. If A resolves after B, A's response must be discarded — key the applied response to the email value at call time (identical guard to `LoginForm`'s `pendingLookupEmail`-based race guard, Story 14.4 AC-8) and only call `setPreAuthTheme()` if the current email still matches the email the resolving lookup was issued for.
- **Edge/failure — lookup network/server error:** Falls open to base theme (`setPreAuthTheme(null, null)`), identical to `LoginForm`'s `catch` block — never a hung or broken registration form.
- **Edge — repeated blur on an unchanged email:** Blurring the same already-resolved email a second time (e.g. tab away and back) MAY re-fire the lookup (idempotent, side-effect-free on the server) — no de-duplication guard is required here the way `LoginForm`'s AC-11 double-click guard is required for its explicit submit button, since a blur event triggering an extra idempotent read-only network call is not a user-facing double-submission risk. Do not over-build a dedupe guard beyond the race guard above.

### AC-2: `RegisterForm` resolves org branding for a pre-filled, read-only email (invitation flow)

**Given** a user on `/register?invitationToken=...&email=...` (the invitation flow — email is pre-filled and rendered `readonly`, existing behavior unchanged), **when** the component mounts, **then** `RegisterForm` fires the same domain-lookup call once, using `prefillEmail`, without waiting for a blur event that a read-only field will never receive from the user.

- **Positive:** Alex lands on `/register?invitationToken=abc&email=alex%40acme.com`. On mount, `RegisterForm` calls `lookupSsoDomain(fetch, "alex@acme.com")`, resolves `acme-brand`, applies it. Alex never has to interact with the (read-only) email field to see branding.
- **Positive — already-applied from the accept page (AC-3):** If Alex arrived via `(auth)/invitations/accept`'s own redirect (not a direct deep link), the theme may already be applied from AC-3's earlier lookup for the identical email — this mount-time lookup re-resolving the same email is redundant-but-harmless (idempotent read, same fail-open guarantees), not a bug to special-case or skip. Do not add cross-page state-passing to avoid this one extra read-only call; keeping each page independently correct is simpler and matches this story's "reuse the existing call, no new mechanism" mandate.
- **Edge/failure — invitation email has no org-theme mapping:** Falls open to base theme (`theme` absent from the lookup response), identical reasoning to AC-1's miss case. No special-casing for the invitation flow vs. free registration — both paths resolve through the exact same client function and fail-open logic.
- **Edge — `invitationToken` present but `email` query param missing or empty:** `prefillEmail` defaults to `''` (existing behavior, `+page.svelte`'s `?? ''` fallback, unchanged). No lookup fires for an empty string — reuse the same client-side email-validity gate from AC-1 (an empty string is not a valid email) rather than issuing a doomed lookup call.
- **Edge — redundant identical write from a slower `(auth)/invitations/accept` lookup (Round 3 elicitation, Edge-Case Stress Test):** If the user arrived via the accept page's own redirect (AC-3), that page's lookup for the same `peek.email` may still resolve *after* this mount-time lookup has already applied the theme. Since both calls resolve the same email to the same theme in every realistic case, this is a harmless redundant write of an identical value, not a race requiring a cross-page guard — no code change implied, noted here only so a reviewer doesn't mistake the double-write for a bug.

### AC-3: `(auth)/invitations/accept` resolves org branding as soon as the invitation peek returns an email, before its own redirect

**Given** a visitor loads `/invitations/accept?token=...`, **when** `peekInvitation()` successfully resolves `{ email, ... }`, **then** the page fires the same domain-lookup call (fire-and-forget, never blocking or delaying the page's own existing redirect logic) so that whichever page it redirects to next (`/register` or `/login`) already has branding applied via the shared rune, rather than showing a base-theme flash during the brief "Checking your invitation..." state and then a jump to branded on the next page.

- **Positive — redirects to `/register` (no account yet):** `peekInvitation()` resolves `{ email: "alex@acme.com", accountExists: false, ... }`. The page calls `lookupSsoDomain(fetch, "alex@acme.com")` (not awaited before the `goto('/register?...')` call — the redirect must not wait on this read) and applies the result via `setPreAuthTheme()`. Because `goto()` is a client-side SPA navigation (no full page reload, confirmed — `(auth)/+layout.svelte` is not remounted across it), the rune state set here survives into the `/register` page's render, so Alex sees `acme-brand` from the very first paint of `/register`, not a flash-then-branded transition.
- **Positive — redirects to `/login` (account exists, not authenticated):** Same lookup fires for `peek.email` before the `goto('/login?next=...')` call. `/login`'s own `LoginForm` starts fresh at Step A regardless (this story does not add an email-prefill prop to `LoginForm` — out of scope, see below) — the org branding, once resolved from `accept`'s lookup, persists into the login screen's initial render via the same shared rune, even though the user still has to re-type their email to actually sign in.
- **Edge/failure — `peekInvitation()` itself fails (invalid/expired token, status → `'invalid'`):** No email is ever resolved, so no lookup is attempted — the "Invitation not available" error message renders in the base theme. This is correct, not a gap: there is no email to look up, and inventing one from an untrusted/unparsed token would be a new, unjustified surface.
- **Edge/failure — the domain-lookup call itself fails (network/server error) while `peekInvitation()` succeeded:** Falls open to base theme (`setPreAuthTheme(null, null)` or simply never called — same net effect), and — critically — **must not** affect the page's own accept/redirect flow in any way. Add an explicit test asserting a rejected/erroring domain-lookup call never throws into `run()`'s own try/catch blocks or delays/blocks the `goto()` calls (wrap the lookup in its own isolated `try`/`catch`, or use `.catch()` on the fire-and-forget promise — never let it propagate into the surrounding invitation-acceptance logic).
- **Edge — the `getCurrentUser()`/`acceptInvitation()` success path (already-authenticated user accepting immediately, no redirect to register or login at all):** This story's branding only matters for the pre-auth window between page load and whichever page/action follows — an already-authenticated user who accepts immediately and lands on `/projects/:id` (an `(app)` page) picks up branding from the `(app)` layout's own, unrelated, already-shipped Story 16.4 AC-2 authenticated resolution path, not from this story's pre-auth lookup at all. No new behavior needed here; noted so a reviewer doesn't expect this story to touch the authenticated-acceptance path.

### AC-4: rate limits

**Given** `POST /domain-lookup` already carries Story 14.4's `{ max: 20, timeWindowMs: 15 * 60 * 1000 }` budget (unchanged, unmoved, no new endpoint), **when** this story adds two more call sites (`RegisterForm`'s blur/mount triggers, `invitations/accept`'s peek-resolution trigger), **then** no new rate-limit threshold is introduced — the added call sites ride the existing budget, and AC-1's client-side email-validity gate keeps blur-triggered call volume comparable to (not multiplied beyond) `LoginForm`'s existing submit-triggered volume.

- **Positive:** A user filling out `/register` normally (one blur past the email field, maybe one correction) issues 1-2 lookup calls, well within the existing 20-per-15-minutes budget shared with `/login`.
- **Edge/failure — a user rapidly toggling the email field to probe the budget:** Eventually receives `429` from the existing, unchanged rate limiter (Story 14.4's own tested behavior) — this story adds no new test burden here beyond confirming the existing `429` response is handled the same fail-open way (`setPreAuthTheme(null, null)`, no error surfaced to the registration/invitation flow itself, which never depended on this call succeeding).

### AC-5: RLS / tenant isolation

**Given** this story adds zero new backend routes, columns, or queries, **when** `make check-rls` runs, **then** it passes clean with no changes — cross-tenant isolation for the reused `domain-lookup` response is entirely governed by Story 16.4 AC-4's existing guarantees (the `org_sso_domains.domain` unique index), unchanged and unaffected by which pre-auth page happens to call it.

- **Positive:** `make check-rls` reports unchanged clean output, identical to pre-story baseline.
- **Edge — no new cross-tenant surface:** A visitor on `/register` or `/invitations/accept` can, at most, learn the same "does this domain have SSO + a custom default theme name" bit Story 16.4's Red Team review already accepted as non-sensitive, self-chosen, org-admin-controlled display data (see 16.4's own Red Team section) — calling the identical endpoint from two additional pre-auth pages does not create a new information class, only additional call sites for information already exposed via `/login`.

### AC-6: audit behaviour

**Given** this story's two new call sites are both read-only (`POST /domain-lookup` is unchanged, and this story writes nothing new to any table), **when** either call fires, **then** no audit entry is written — matching Story 16.4 AC-5's explicit "read-only theme resolution is never audited" convention.

- **Positive:** Registering a new account or accepting an invitation writes exactly the same audit entries it did before this story (registration/invitation-acceptance events, both pre-existing and unrelated to theming) — no new audit event type is introduced.
- **Edge — do not add one "for completeness":** Per-page-load audit logging for a routine, unauthenticated branding read would be pure noise at request-volume frequency, identical reasoning to 16.4 AC-5.

### AC-7: auth/session lifecycle

**Given** the `preAuthThemeName`/`preAuthThemeCss` runes are client-only, unauthenticated, page-session-scoped state (Story 16.4 Task 7.2 — deliberately never persisted server-side, never part of any session/JWT), **when** this story's two new call sites set them, **then** the same lifecycle rules already established for `/login` apply unchanged: a full page reload (not a SPA `goto()`) resets the rune to its initial `null`/`null` state, and no MFA gate applies to any of these reads (`requireAuth: false` on `POST /domain-lookup`, unchanged since Story 14.4).

- **Positive:** Alex navigates `accept → register` via the app's own client-side `goto()` calls (AC-3) — the rune survives, no re-lookup strictly required for branding continuity (though AC-2's mount-time lookup still fires redundantly-but-harmlessly, as noted).
- **Edge — a user manually refreshes `/register` mid-flow (full page reload):** The rune resets to `null`/`null` on reload (no server load seeds it — confirmed unchanged from 16.4's own documented asymmetry between `(app)`'s SSR-seeded rune and `(auth)`'s client-only one). `RegisterForm`'s own mount-time (AC-2) or blur-triggered (AC-1) lookup re-resolves the branding fresh within one round trip — a brief, one-time base-theme flash on manual reload is accepted as-is, identical in kind to `/login`'s own pre-existing behavior on reload (not a regression this story introduces, since `/login` already has this exact characteristic today).

### AC-8: concurrent access

**Given** a single browser tab can only ever have one email field per page in flight at a time (no multi-tab-shared state — the rune is per-page-session, per Story 16.4's design), **when** two lookups for different emails race (AC-1's out-of-order case), **then** the resolution logic keys strictly to the email value at call time and discards a stale response — no server-side concurrency concern exists here at all (this is a pure client-side read-path race, not a write race like Story 16.4 AC-7's PATCH route).

- **Positive/Edge:** Fully covered by AC-1's out-of-order-response race test case; no additional server-side concurrency test needed since no write path exists in this story.

- **Positive/Edge:** No test needed beyond confirming no new `req.log` call was added anywhere in this story's diff (a code-review-time check, not an automated assertion) — mirrors 16.4 AC-10's own "no new log line for the read paths" edge case verbatim.

## Out of Scope (explicit — do not scope-creep)

- **Adding an email-prefill prop to `LoginForm`.** AC-3's "redirects to `/login`" case notes that a returning-invitee's email isn't carried into `LoginForm`'s Step A. Prefilling it would be a small, plausible follow-up (and would let that redirect also skip straight to Step B) but is a distinct, `LoginForm`-scoped change unrelated to this story's actual mandate (pre-auth branding) — not built here.
- **Zero-input pre-auth branding on `/register` (before any email exists on the page at all, e.g. a direct visit to `/register` with no query params and no user input yet).** Same structural impossibility Story 16.4 already documented for `/login`'s very first render — there is no email to resolve an org from yet. Unchanged, not reopened by this story.
- **A general-purpose email-domain-to-org resolution mechanism for orgs without SSO.** Same explicit non-goal Story 16.4 already established — this story reuses `org_sso_domains` exactly as-is, adding no new domain-mapping table or admin UI.
- **Any change to `POST /domain-lookup`'s backend implementation, request/response schema, or rate-limit configuration.** This story is client-side-only, per its own scope note in `sprint-status.yaml` — the endpoint Story 16.4 built is reused verbatim, unmodified.
- **Branding the invitation-acceptance success/error states differently based on theme (e.g. themed error illustrations).** Only the shared `(auth)` layout's existing `data-theme`/CSS-injection mechanism is exercised — no new per-status visual treatment.
- **Persisting or caching the resolved pre-auth theme across a full page reload.** Same explicit non-goal as Story 16.4 (AC-7 above) — client-only, session-scoped, resets on reload by design.

### Self-registration branding is cosmetic-only, not a trust signal (judgment call, flagged explicitly)

A user self-registering a **new, independent organization** (no invitation token) who happens to type an email at a domain that maps to a *different, existing* org (e.g. Jordan typing `jordan@acme.com` while creating a brand-new "Jordan's Org") will transiently see Acme Corp's branding on the registration form, even though Jordan is not joining Acme Corp at all. This is accepted as-is for these reasons:
- The branding is purely cosmetic UI chrome (a background color/logo-adjacent styling token from a compiled theme) — it carries no functional claim, grants no access, and pre-fills no data tied to the other org (unlike, say, auto-joining Acme Corp, which this story does not do and never touches).
- It is the direct, unavoidable consequence of reusing `POST /domain-lookup` exactly as Story 16.4 designed it — that endpoint's contract is "resolve theme for this email's domain," not "resolve theme only if this email is about to join that org." Splitting those two concepts would require a new, narrower endpoint or a client-side flag distinguishing "join" vs. "create new" intent passed to the lookup — out of scope per this story's "reuse the existing call, no new mechanism" mandate.
- The same transient-branding behavior already exists today, unchanged, for `/login`: typing `jordan@acme.com` into the login screen shows Acme Corp branding regardless of whether Jordan actually has an Acme Corp account — this story is not introducing a new category of behavior, only extending an already-accepted one to two more pages.

If this proves confusing in practice (support tickets, user feedback), the correct escalation is a follow-up story adding an explicit `intent: 'join' | 'create'` parameter to the domain-lookup call and having the org-creation flow specifically suppress branding — not a silent workaround in this story.

### Pre-Mortem: production failure scenarios (Round 1 elicitation)

1. **The invitation-accept page's fire-and-forget theme lookup accidentally becomes a blocking `await`, delaying or breaking the accept/redirect flow.** This is the single largest risk this story introduces, since `run()`'s existing logic is security/UX-relevant (getting a user into their invited project) and this story's addition is purely cosmetic. **Mitigation:** Task 2.2/2.3 explicitly require the lookup call to never be awaited before a `goto()`, with its own isolated error handling. Add a regression test (Task 2.4) that simulates a slow/never-resolving domain-lookup promise and asserts the `/register` or `/login` redirect still happens promptly regardless.
2. **`RegisterForm`'s blur-triggered lookup fires on every keystroke instead of on blur, due to a wiring mistake (e.g. binding to `oninput` instead of `onblur`).** Would multiply call volume dramatically past what AC-4 assumes and could exhaust the shared rate-limit budget during normal typing. **Mitigation:** Task 1.3 explicitly specifies `onblur`; add a test asserting no lookup call fires on `oninput` alone (only on blur/mount).
3. **The mount-time lookup for the invitation flow (Task 1.4) fires even when `invitationToken` is absent, wasting a call on every plain `/register` visit regardless of whether an email is present.** **Mitigation:** Task 1.4 explicitly gates on `invitationToken` being set AND `prefillEmail` being non-empty; add the explicit negative test already listed in Task 1.5.
4. **A fast-typing user clicks "Create account" immediately after typing their email, before ever blurring the field naturally (e.g. Tab-navigates straight from email to password, never triggering a standalone blur on email until form submission itself fires a implicit blur).** If the implementation mistakenly makes the branding lookup a *precondition* for allowing submission (e.g. disabling the submit button until `pendingThemeLookupEmail` clears, copying `LoginForm`'s `disabled={pendingLookupEmail === email}` pattern too literally onto a button that submits the whole registration, not just a "Continue" step), registration itself would be blocked by a purely cosmetic, best-effort call — a severity jump from "wrong branding" to "can't register." **Mitigation:** Task 1 must NOT gate the "Create account" submit button on the theme-lookup's in-flight state at all (unlike `LoginForm`'s Step-A "Continue" button, which legitimately gates on its lookup because that lookup's result determines which step renders next). Added explicit language to Task 1.2/1.3 below and a new negative test in Task 1.5 asserting registration submission succeeds even while a theme lookup is still in flight.
5. **Self-registration branding (AC-1) causes real user confusion or a support burden** — a self-registering user creating their own brand-new org sees a different, existing org's branding mid-form, and may believe (incorrectly) that they are joining that org, or that their new org has somehow inherited that org's theme. Explored further under Red Team (Round 2) and given a final disposition under Stakeholder Round Table (Round 5) below, since it touches product/UX judgment beyond a pure engineering failure mode.

Mitigation for scenario 4 folded into Task 1 (see updated task text below); scenario 5 carried forward to Rounds 2 and 5 rather than resolved here.

### Red Team: adversarial review (Round 2 elicitation)

Attacking this story's two new call sites from an outside-attacker and a confused-insider perspective:

- **Org/theme enumeration via two additional pre-auth pages.** Story 16.4's Red Team round already accepted that `POST /domain-lookup` lets any anonymous caller learn "does this domain have SSO + a custom theme name" — a non-sensitive, org-admin-chosen display string. This story adds no new information class and no new endpoint; it only adds two more *client-side* pages that happen to call the same already-public endpoint. **Verdict: not a new severity class**, identical reasoning to 16.4's own accepted baseline — but worth stating explicitly here since a reviewer auditing this story in isolation (without re-reading 16.4) might otherwise flag it as new exposure.
- **CSS-injection via the invitation-accept page's fire-and-forget lookup.** Already fully mitigated by construction, same as 16.4: `theme.css` only ever contains 16.1's compile-time-sanitized output for a name currently present in `getCompiledThemes()`; this story adds no new code path that accepts or reflects attacker-supplied content, and the delivery mechanism (`<svelte:element this="style">` in `(auth)/+layout.svelte`) is entirely unmodified by this story. **Verdict: no new surface.**
- **Self-registration branding as a phishing/social-engineering amplifier (the sharper framing of Pre-Mortem scenario 5).** Consider: an attacker registers `attacker-org` and separately controls (or spoofs, via a lookalike UI screenshot) a domain that happens to collide with a legitimate, well-known org's `org_sso_domains` mapping — no, this doesn't actually work as an attack, because `org_sso_domains` mappings are admin-configured by the legitimate org itself (Story 14.4), not attacker-controlled, and the domain-lookup only ever resolves branding for domains a real org has already registered. An attacker cannot make an arbitrary victim's self-registration page show attacker-chosen branding — they can only make it show a *real* org's *real*, self-chosen branding for a domain that org already owns. **Verdict: not an exploitable phishing vector** — this is a genuine UX-confusion risk (Pre-Mortem #5), not a security vulnerability. Explicitly downgraded from a Red Team finding to a Stakeholder/UX judgment call (Round 5) on this basis.
- **Rate-limit budget exhaustion as a denial-of-branding (not denial-of-service) griefing vector.** An attacker could script rapid email-field blur/re-blur cycles against `/register` to exhaust the shared `{max:20, timeWindowMs:15min}` budget for a specific victim IP/session, but this budget is already shared with `/login` today (Story 14.4) and is per-caller (not global), so this griefs only the attacker's own session, not other users'. **Verdict: no new abuse vector**, identical to 16.4's own accepted rate-limit posture.

No new mitigations required from this round — every avenue traced back to either an already-accepted 16.4 baseline or a non-exploitable theoretical path. Confirms AC-4/AC-5's existing "no new surface" framing rather than adding to it.

### Edge-Case Stress Test (Round 3 elicitation)

Walking every boundary condition this story's own AC/task list touches, to confirm nothing is missing:

- **`RegisterForm`'s email field is blurred, then the user re-focuses it and blurs again without changing the value.** Already addressed in AC-1's own "repeated blur on an unchanged email" edge case — confirmed no dedupe guard needed, an idempotent extra read is acceptable. No new case.
- **The invitation-accept page's peek resolves an email, the theme lookup for it is in flight, and the user closes the tab or navigates away (via browser back/forward, not the page's own `goto()`) before it resolves.** The in-flight `fetch` is simply abandoned by the browser/SvelteKit's own navigation lifecycle (no explicit `AbortController` wiring exists for this call, nor for `LoginForm`'s equivalent call in 16.4 — consistent, not a regression) — no error surfaces anywhere since the promise's resolution, if it ever completes, targets a rune that no page currently reads if the `(auth)` layout itself has been torn down. **Verdict: no new case needed**, same implicit behavior as every other unawaited fetch in this codebase's pre-auth flows.
- **A theme with an extremely long compiled CSS payload (approaching whatever compile-time size cap 16.1 established) resolves on `/register`, on a slow connection.** Identical to 16.4's own Pre-Mortem scenario #1 (already confirmed covered by 16.1's existing compile-time size bound, no new control needed) — this story doesn't change the payload, only which pages request it. No new case.
- **Two different pre-auth pages set the shared `preAuthThemeName`/`preAuthThemeCss` rune in close succession** — e.g. the invitation-accept page's lookup (AC-3) resolves *after* the user has already navigated to `/register` and `RegisterForm`'s own mount-time lookup (AC-2) has already resolved and set the rune. Since both lookups are for the *same* `peek.email`/`prefillEmail` value (the invitation flow's email is threaded through unchanged via the `?email=` query param), both calls resolve to the same theme in the common case — no conflict, just a redundant identical write (already noted as "redundant-but-harmless" in AC-2). The one genuine edge case: if `accept`'s lookup is unusually slow and resolves *after* `RegisterForm`'s own faster mount-time lookup already applied the theme, `accept`'s stale-but-identical write is a harmless no-op (same value). **Verdict: no race-guard needed across pages** (unlike the *within-one-page* race AC-1 already guards against), since both writes target the same value for the same email in every realistic case — added as an explicit note to AC-2 below rather than a new task, since no code change is implied.
- **The `/register` route's org-name field (shown only when `!invitationToken`) renders under another org's injected CSS with a theme that happens to have poor contrast for that specific field's styling.** A real but purely cosmetic risk, not a functional one — no theme-specific contrast auditing is in this story's scope (themes are compiled and validated for basic well-formedness by 16.1, not accessibility-audited per-story). **Verdict: no new case**, out of scope, consistent with 16.1/16.2/16.4 never having taken on per-theme accessibility auditing either.

One clarifying note added to AC-2 (see updated AC text below); no Task changes from this round otherwise — every stress-tested boundary was already correctly handled by the existing design.

### Occam's Razor: scope simplification (Round 4 elicitation)

Checking whether this story's design carries any unjustified complexity relative to its Medium-High-scoped retro finding:

- **Considered: drop the mount-time lookup (AC-2/Task 1.4) and rely solely on the invitation-accept page's own lookup (AC-3) plus rune persistence across the `goto()`.** Rejected: this would silently break the documented "direct deep-link to `/register?invitationToken=...&email=...`, skipping the accept page entirely" case (AC-2's own second positive example) — a real, reachable path (e.g. a user who bookmarked or was sent the `/register` URL directly rather than the original invitation link). Removing Task 1.4 would leave that path permanently unbranded with no fallback. **Kept as-is** — the two call sites are not redundant, they cover genuinely different entry paths.
- **Considered: drop the blur-triggered lookup (AC-1/Task 1.3) for self-registration entirely, given Round 2's finding that it's a UX-confusion risk rather than a security one, and Pre-Mortem's flagging of it as the story's most debatable inclusion.** This is the single largest scope question in the story and is deliberately **not** resolved by simplification alone — carried forward to the Stakeholder Round Table (Round 5) below for a final product-level disposition rather than an engineering-convenience cut, since removing it would also remove real value for the (arguably more common) case of an invited user typing their own email manually because the invitation link's `email` param was stripped or they navigated to `/register` fresh and typed the same email their invitation used.
- **Considered: a single shared helper function (e.g. `resolveThemeForEmail(email, isReadonlyPrefill)`) exported from a shared module and imported by both `RegisterForm.svelte` and the invitation-accept page, rather than two independent implementations.** Evaluated and **adopted** — the race-guard/fail-open logic (AC-1's out-of-order guard, fail-open to `setPreAuthTheme(null, null)`) is identical in shape to `LoginForm.svelte`'s own `submitEmailStep()` resolution logic, and duplicating it a third time (a fourth, counting `LoginForm`) invites drift. **Added as a new Task 0** below: extract a small, pure-ish helper (keeping the actual `$state` race-tracking local to each caller, since Svelte runes aren't natively shareable as a return value across component boundaries the way a plain closure would be — the helper wraps the fetch+fail-open logic, not the reactive state) to `apps/web/src/lib/components/auth/form-model.ts` (the existing shared module `LoginForm`/`RegisterForm` both already import from) rather than leaving three near-identical inline implementations across `LoginForm.svelte`, `RegisterForm.svelte`, and `invitations/accept/+page.svelte`. This is a simplification that reduces, not adds, total complexity — flagged here rather than silently added, per this story's own no-scope-creep discipline, since it does touch `LoginForm.svelte` (a refactor of already-shipped 16.4 code, not new behavior) to extract its existing logic into the shared helper.

Task list revised below: new Task 0 (extract shared resolver), Task 1 renumbered to consume it, `LoginForm.svelte` added to Project Structure Notes' modified-files list as a refactor-only touch (behavior-preserving, covered by its own existing tests continuing to pass unchanged).

### Stakeholder Round Table (Round 5 elicitation) — final disposition of the one remaining open question

Convening the four perspectives most affected by Pre-Mortem #5 / Red Team's downgraded finding / Occam's Razor's deferred question — **should self-registration (`RegisterForm` with no `invitationToken`) resolve and display org branding at all (AC-1), given it can show a real user a real-but-unrelated org's branding while they create their own independent org?**

- **Product/PM view:** The confusion risk is real but narrow and self-correcting — Jordan sees Acme Corp's colors for a few seconds while typing, and nothing in the form's copy or structure implies "you are joining Acme Corp" (the org-name field, visible specifically in the no-invitation case, makes clear Jordan is naming their *own* org). The alternative — suppressing branding for self-registration entirely — would also suppress the legitimate, common case of an invited user typing their own email at their own company's domain and expecting to see their company's look-and-feel, matching what they'd see on `/login`. **Recommends keeping AC-1 as scoped.**
- **Security view:** Already established under Red Team (Round 2) that this is not an exploitable vector — no attacker can inject or spoof branding for a domain they don't legitimately administer. **No objection to keeping AC-1**; notes this is a pure UX call, not a security one, and defers to Product/UX on the final call.
- **UX/Support view:** Agrees the risk is real but low-severity and low-frequency (requires a self-registering user to type an email at a domain that happens to be both SSO-mapped *and* themed by an unrelated org — a fairly specific coincidence, not the common self-registration path, which more often uses a personal or brand-new-company email with no existing org mapping at all). If this does generate confusion in practice, the cheapest possible mitigation is a copy change (e.g. a small caption near the org-name field: "You're creating a new, independent organization" — already implied by the existing surrounding copy on `/register`, per the current `+page.svelte`'s subtitle text "Create a new, independent organization in this vault," visible in the no-invitation case) rather than suppressing branding outright. **Recommends keeping AC-1, notes the existing subtitle copy already substantially mitigates the confusion risk and requires no story change.**
- **Admin/end-user (Riley) view:** An org admin who configured `acme-brand` as their org's default theme (Story 16.4) would reasonably expect it to appear consistently across every pre-auth surface that can resolve their domain — including a case where a departed-and-rejoining former employee, or someone incorrectly assuming they need to "sign up" rather than being invited, types their `@acme.com` email into `/register`. **No objection; mildly prefers the consistency AC-1 provides.**

**Final disposition (binding for this story, not to be re-opened during implementation):** AC-1 (self-registration branding) **stays exactly as scoped** — all four perspectives converge on keeping it, with the UX/Support view's observation that the existing `/register` subtitle copy already substantially addresses the confusion risk, requiring no additional story scope. This closes the one remaining open judgment call raised across Rounds 1, 2, and 4; a reviewer re-raising it during C2 code review should treat this section as the recorded resolution, not a gap.
