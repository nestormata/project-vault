# Story 17.3: Share History, Expiry Enforcement & Rotation-Recommended Nudge

Status: in-progress

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a project member who has shared a credential (or has reveal access to one that's been shared),
I want a complete, filterable share history, a share that actually expires as a recorded event rather than only on next access, and a persistent "shared — rotation recommended" nudge that clears itself the moment I actually rotate the credential,
so that I always know who has (or had) access to a secret's value, the credential's history is trustworthy even for shares nobody ever opened again, and the product tells me — accurately and up to date — when a shared secret still needs rotating.

### Persona journey stub

**Morgan (project member, sharer)** opens the credential detail page for a credential they've shared before. The existing **Shares** tab (built in 17.1, extended in 17.2) now supports filtering by status (active / viewed / revoked / expired / superseded) and paginates once history grows past a page, so Morgan can find a specific old share without scrolling an unbounded list. Morgan sees a persistent **"Shared 3 days ago — rotation recommended"** badge on the credential detail header (new in this story), with a link straight into rotation initiation, and a **Dismiss** action that requires typing a short reason before it clears ("Rotated out of band", "False alarm", etc. — any non-empty text). Morgan initiates a rotation and promotes it (Story 5.6's flow); the moment promotion succeeds, the badge disappears on next page load — without Morgan having to visit the Shares tab or do anything else — because every outstanding share of that credential (or the specific rotated field, for a multi-field secret) has been automatically marked `superseded` by the promote transaction itself.

**Riley (org admin, auditor)** opens the Shares tab weeks later and sees a share that was never revoked and never viewed, correctly showing `expired` (not stubbornly stuck at `active`, and not silently absent) — because a scheduled sweep, not only the recipient's own (never-taken) access attempt, transitioned and audited it. Riley can also see, in the credential's activity, a distinct `credential.share_superseded` entry from the day Morgan promoted the rotation, explaining exactly why three previously-active shares all flipped state at once.

**Priya (external recipient, no account, from Story 17.2)** — no change to her experience in this story; her link still resolves to expired/used/revoked exactly as before. Her share's eventual expiry is now recorded, and if a rotation is promoted on the shared field before she ever opens the link, her link now correctly reads "no longer available" instead of quietly ceasing to work for an unexplained reason server-side.

## Acceptance Criteria

### Share History

1. **Shares tab supports status filtering.** `GET /:projectId/credentials/:credentialId/shares` (`apps/api/src/modules/credential-shares/routes.ts`) accepts an optional `status` query parameter (one of `active`/`viewed`/`revoked`/`expired`/`superseded`); when present, `listSharesForCredential` (`apps/api/src/modules/credential-shares/service.ts`) filters to that status in addition to its existing `orgId`/`credentialId`/`sharedByUserId` (member) or unrestricted (admin/owner) scoping — the admin-sees-everyone behavior from 17.1's PR #251 patch is unchanged, filtering is additive. Example: Morgan has 12 shares total for credential "Stripe Prod" (5 `active`, 3 `revoked`, 2 `expired`, 2 `superseded`); `GET .../shares?status=superseded` returns exactly the 2 superseded rows. Edge case: an invalid `status` value (e.g. `?status=bogus`) returns `422`, not a silent empty result or a 500 from an unconstrained SQL `IN`.

2. **Shares tab paginates.** The same list route accepts `limit` (default 25, max 100) and `offset` (default 0) query parameters, mirroring the existing `limit`/`offset` convention already used by rotation history (`apps/api/src/modules/rotation/service.ts`'s `MAX_ROTATION_HISTORY_ROWS_PER_QUERY`-guarded query, ~line 1872) rather than inventing a cursor-based scheme for this story. The response shape gains a `total` count (a separate `COUNT(*)` query with the same filters, no `status`/pagination applied to the count) alongside `items`, so the web UI can render "showing 1-25 of 41" / a Next button without a second round-trip. Example: 41 shares exist; `?limit=25&offset=25` returns the remaining 16 with `total: 41`. Edge case: `limit=500` is clamped server-side to the max (100), not rejected — same "clamp, don't 400, on an over-large but otherwise well-formed limit" convention used elsewhere in this codebase for list endpoints (confirm the exact precedent at implementation time and match it, don't invent a new error-vs-clamp policy here).

3. **No new "unified cross-recipient-type view" work needed — already unified.** Confirmed by reading the shipped `listSharesForCredential`: it already returns both `recipient_type = 'user'` (17.1) and `recipient_type = 'external'` (17.2) rows from the same query, and `serializeShare` already emits `recipientType`/`recipientEmail` alongside member fields (17.2's Task 8.4 already wired the web UI to render both). This AC exists only to document that this was **verified, not assumed** — do not build a second listing path or a "merge two lists" UI pattern; the existing single list is already the unified view AC-1/AC-2 extend.

4. **Shares tab surfaces `field_key` alongside status.** Confirmed gap: `serializeShare`'s current output includes `fieldKey` (it's a direct column passthrough), but the web UI's Shares tab table (17.1 Task 7.1) does not render a dedicated "Field" column — it was out of scope for 17.1/17.2, which only tested whole-credential shares in their UI screenshots. Add a "Field" column (showing the field's display name via the same `fieldMetaForResponse` helper used elsewhere, or "Whole credential" when `fieldKey` is null) so Morgan can distinguish which of a multi-field secret's shares is which at a glance. This is a UI-only change (Task 7 below); no API shape change beyond what AC-1/AC-2 already add.

### Expiry Enforcement (audited transition, not lazy-only)

5. **New `AuditEvent.CREDENTIAL_SHARE_EXPIRED` (`credential.share_expired`), added to `packages/shared/src/constants/audit-events.ts` next to the existing `CREDENTIAL_SHARE_*` trio.** Every transition of a share's `status` from `active` to `expired` — whichever code path discovers it — writes this event via the same fail-closed convention (`writeHumanAuditEntryOrFailClosed` for the session-bound 17.1 path, `writeSystemAuditEntryOrFailClosed` for paths with no human actor, matching 17.2's own precedent for its external reveal path) as the rest of the `credential.share_*` family. Example: a share created by Morgan with a 24h expiry is never opened by Riley; some time after the deadline passes, the share transitions to `expired` and an audit row is written recording the share id, credential id, and that the transition was system-driven (no actor), not "nobody ever finds out this happened." Edge case: a share that is already `revoked` or `viewed` when its `expiresAt` passes does **not** get a spurious `expired` transition or audit entry — the transition only applies to shares still `active` at the moment expiry is discovered (matches the existing `lazilyExpireShareIfDue`'s own guard: `if (share.status !== 'active' ...) return share`).

6. **`lazilyExpireShareIfDue` (`apps/api/src/modules/credential-shares/service.ts`) now writes the audit event described in AC-5, inside the same transaction as its status UPDATE.** This function is already called from both `findShareByToken` (17.1's session-bound metadata GET) and `external-service.ts`'s reveal-metadata equivalent (17.2) — today it silently flips `status` with zero audit trail (confirmed by reading its current body: a bare conditional `UPDATE ... RETURNING`, no audit call at all). This story adds the audit write to the existing function so both call sites inherit it for free, rather than duplicating the write at each call site. Example: Priya opens an already-expired external link; the metadata GET's lazy-expiry check flips the share to `expired` and writes `CREDENTIAL_SHARE_EXPIRED` in the same request that serves her the "this link has expired" response.

7. **New scheduled sweep worker, `apps/api/src/workers/credential-share-expire.ts`, following the established per-candidate-transaction pattern (`rotation-recover.ts`/`rotation-stale-staged-alert.ts` — Story 5.6's own precedent, one transaction per row, never a single transaction spanning multiple rows) closes the "nobody ever opens the link again" gap.** Scans `WHERE status = 'active' AND expires_at < now()`, and for each matching row (own transaction): flips `status` to `expired`, writes `CREDENTIAL_SHARE_EXPIRED` (AC-5), same as the lazy path. This is required — not merely nice-to-have — because AC-1/AC-2's Share History listing must show an accurate, up-to-date status for shares that are never re-accessed by anyone (the epic's own security-review §1.2 explicitly specified this as part of the original design: "`expires_at` is enforced both at query time... and via a scheduled sweep... so an expired token reads as fully gone even if the sweep hasn't run yet" — 17.1 built the query-time half only and explicitly deferred the sweep to this story). Register on a cron matching the other daily/periodic workers' registration site (`apps/api/src/main.ts`, following 5.6's `rotation-stale-staged-alert` registration as the most recent precedent) — a frequent interval (e.g. hourly) is more appropriate here than 5.6's daily cadence, since share `expiresAt` windows are measured in hours, not weeks; **judgment call for the dev agent, document the chosen interval in the Dev Agent Record.**

8. **ADR — lazy-check-plus-sweep, not sweep-only or lazy-only (decide and record).** Considered: (A) lazy-only (today's shipped behavior, but now audited) — rejected as the sole mechanism because it leaves Share History (AC-1/AC-2) inaccurate for shares nobody ever revisits, which defeats the point of a history view; (B) sweep-only, removing the lazy check — rejected because it would let an already-expired token read as `active` for up to one sweep interval on a viewer's live reveal attempt, a real (if narrow) window where a stale-but-not-yet-swept link's metadata GET still shows "you have a share" when it shouldn't. **Decision: both (A) and (B)**, exactly matching the epic security review's own original design intent — the lazy check is a self-healing belt on the read path, the sweep is the suspenders that keeps the historical record accurate even absent any read. Record this as an explicit ADR in Dev Notes (not just this AC), since a future maintainer might otherwise "simplify" by removing one of the two paths.

9. **Story 5.6's `stale-staged` alert (14-day, non-blocking, distinct from the 1h crash-recovery mechanism) is already fully built — confirm only, build nothing.** Verified by reading `_bmad-output/implementation-artifacts/5-6-staged-primary-secondary-rotation-state-machine.md`'s Dev Agent Record: `apps/api/src/workers/rotation-stale-staged-alert.ts` (new worker), `STALE_STAGED_ROTATION_THRESHOLD_DAYS` env var (default 14), `AuditEvent.ROTATION_STALE_STAGED_DETECTED`, and the `rotationStaleStagedAlertsTotal`/`rotationsPromotedUnretiredCount` metrics were all shipped and merged as part of Story 5.6, which is `done`. The sprint-change-proposal's Round 2/Round 4 elicitation findings that originally motivated this alert (§7) are the same findings that ended up implemented there, not here — this story's own scope (per its own bracketed note in the sprint-change-proposal, §4.2) is Expiry Enforcement for **shares**, not rotations. Do not re-implement or duplicate any part of the stale-staged mechanism under this story; if a dev agent finds itself writing a second `staged`-rotation-staleness worker, that is a sign this AC was missed, not a sign more work is needed here.

### Rotation-Recommended Nudge (FR125) + Supersession on Promote

10. **New table `credential_share_nudge_dismissals` (migration, next free number — re-verify against `packages/db/src/migrations/meta/_journal.json` immediately before writing, per this project's recurring migration-numbering-collision risk flagged by every prior story in this epic).** Columns: `id uuid PK`, `org_id` (orgScoped), `credential_id uuid FK credentials(id) ON DELETE CASCADE`, `field_key text` nullable (NULL = whole-credential bucket, mirroring `credential_shares.field_key`'s existing single-nullable-text-column convention — not an array), `dismissed_by uuid FK users(id) ON DELETE RESTRICT`, `dismissed_at timestamptz NOT NULL DEFAULT now()`, `reason text NOT NULL` (FR125's "explicitly dismissed with a recorded reason" — empty/whitespace-only reason is rejected at the API layer with `422`, this is the load-bearing fix for the sprint-change-proposal's own Round 2 finding: "dismissal must record a reason"). Index on `(credential_id, field_key, dismissed_at DESC)` for the nudge-computation query in AC-11. This is new schema, not an extension of `credential_shares` — a dismissal is a distinct, append-only event (each dismissal is its own row, not an update-in-place flag), so a credential/field's dismissal history is itself auditable without a separate audit-log entry duplicating the same data.

11. **Nudge state is computed, not stored as a boolean flag — derive it from existing data plus the new dismissals table.** `GET` on the credential detail response (or a small new endpoint, dev agent's call — see Dev Notes) includes, per credential and per distinct `field_key` that has ever been shared, a `rotationRecommended` object: `{ active: boolean, mostRecentShareAt: string | null, mostRecentSharedWith: string | null }` computed as: **active = true** iff there exists a `credential_shares` row for that `(credentialId, fieldKey)` bucket with `status != 'superseded'` **and** `createdAt` is after the most recent `credential_share_nudge_dismissals` row for that same bucket (or no dismissal exists at all). Example: credential shared on day 1 (nudge active from day 1) → dismissed on day 5 with reason "acknowledged, will rotate later" (nudge now inactive) → shared again on day 8 (nudge active again, `mostRecentShareAt` = day 8, ignoring the day-1 share for display purposes) → this is the literal "a new share re-triggers the nudge even after a prior dismissal" behavior FR125 implies by scoping dismissal to "until... explicitly dismissed," not "forever." Edge case: a share that is `revoked` or `expired` (but not `superseded`) still counts toward `active` — the nudge's premise is "this secret's value was exposed to someone at some point since the last rotation/dismissal," which revocation or expiry of the *link* does not undo (the recipient may already have seen/copied the value before it was revoked or expired) — only an actual rotation (via supersession, AC-12) or an explicit dismissal clears it.

12. **Promoting a rotation (Story 5.6's `promoteRotation()`, `apps/api/src/modules/rotation/service.ts`) automatically marks matching outstanding shares `superseded` in the same transaction as the promote itself.** New function `supersedeOutstandingSharesForRotation(tx, { orgId, credentialId, targetFields, rotationId })` exported from `apps/api/src/modules/credential-shares/service.ts` (a new one-directional dependency: `rotation` module calls into `credential-shares` module; confirmed safe — `credential-shares` has no existing import from `rotation`, so this does not create a cycle). Scoping rule, matching the epic's own field-scoping precedent: if `targetFields` is `NULL` (whole-secret rotation), **every** outstanding share for the credential is superseded regardless of its own `fieldKey` (a whole-secret rotation invalidates every previously-shared value, field-scoped or not, since the whole record changed). If `targetFields` is a non-null array (field-scoped rotation, Story 13.4), only shares where `fieldKey IS NULL` (whole-credential shares, which exposed the now-stale field too) **or** `fieldKey = ANY(targetFields)` are superseded — a share of an unrelated, unrotated field is left untouched. "Outstanding" means `status IN ('active', 'viewed')` — a `revoked`/`expired` share has no live value to supersede and is left in its existing terminal state, not double-transitioned. Wire the call into `apps/api/src/modules/rotation/routes.ts`'s `POST .../promote` handler (the exact insertion point is between the existing `promoteRotation()` call and the existing `writeRotationPromotedAudit()` call, ~line 1795-1827 as of this story's writing — call it with `secureCtx.tx` so it shares the promote transaction's atomicity guarantee: if the supersession update or its audit write fails, the whole promote rolls back, exactly like every other rotation mutation in this codebase). Example: credential "Stripe Prod" has 2 active whole-credential shares and 1 active share scoped to field `webhook_secret`; a field-scoped rotation targeting `["api_key"]` is promoted — the `webhook_secret`-scoped share is untouched (still `active`), the 2 whole-credential shares are superseded (they exposed `api_key` too). Counter-example: the same rotation, but whole-secret (no `targetFields`) — all 3 shares are superseded.

13. **Each superseded share gets its own `CREDENTIAL_SHARE_SUPERSEDED` (`credential.share_superseded`) audit entry (new `AuditEvent` constant), not one aggregate entry for the whole batch.** Payload includes `shareId`, `credentialId`, `fieldKey`, `rotationId` (linking the supersession to the specific promote that caused it, satisfying FR124's "visible in the credential's history alongside rotation history"), and `recipientType`. Written via `writeHumanAuditEntryOrFailClosed` inside the same transaction as the promote (the actor is the human who clicked Promote — this is not a system-driven transition the way AC-5's expiry sweep is, so use the human-actor variant, mirroring `writeRotationPromotedAudit`'s own actor-attribution pattern rather than `writeSystemAuditEntryOrFailClosed`). Example: the 2 whole-credential shares superseded in AC-12's example each get their own audit row, both carrying the same `rotationId` but distinct `shareId`s — an auditor filtering by `shareId` sees exactly one supersession event per share, not a merged/ambiguous batch record.

14. **`credential_shares.supersededAt` (already an existing column, unused until this story — confirmed by reading `packages/db/src/schema/credential-shares.ts`, no migration needed for this column) is set alongside the `status = 'superseded'` transition.** No new column here; this AC exists to confirm the existing column is finally wired up, not silently left dormant a second story in a row (the same category of "confirm, don't leave an already-provisioned column unused" note 17.2's AC-19 made about `token_hash`'s unique index).

15. **Nudge dismissal endpoint.** New route `POST /:projectId/credentials/:credentialId/nudge/dismiss` (or nested under the existing credential-shares module — dev agent's call, document in Dev Agent Record), body `{ fieldKey?: string, reason: string }`, `minimumRole: 'member'` (same tier as share creation — a project member with reveal access, not just an admin, can acknowledge their own team's shared-secret nudge), inserts a `credential_share_nudge_dismissals` row. Empty/whitespace-only `reason` → `422` (AC-10's load-bearing requirement, tested explicitly). Writes an audit entry (new `AuditEvent.CREDENTIAL_SHARE_NUDGE_DISMISSED`, `credential.share_nudge_dismissed`) recording who dismissed, for which `(credentialId, fieldKey)` bucket, and the reason text itself (the reason is operationally meaningful audit content, not secret material — safe to store verbatim in the audit payload, unlike share tokens/values). Example: Morgan dismisses the whole-credential nudge for "Stripe Prod" with reason "Value was rotated manually outside the tool, updating checklist by hand" — a `credential_share_nudge_dismissals` row and a `CREDENTIAL_SHARE_NUDGE_DISMISSED` audit entry are both written; the nudge badge disappears from Morgan's next page load per AC-11's computation.

16. **Web UI: rotation-recommended badge on the credential detail header.** New badge component, following the existing rotation-status-badge visual pattern (`apps/web/src/lib/components/rotations/rotation-copy.ts`'s badge-class conventions — reuse the styling approach, this is new content not a new visual language), reading "Shared N days ago — rotation recommended" (singular credential-level badge when the whole-credential bucket is active; if only specific fields have an active nudge on a multi-field secret, list them, e.g. "Field `api_key` shared 2 days ago — rotation recommended") sourced from AC-11's computed nudge state, linking directly to rotation initiation (reusing the existing "Rotate" CTA/route), with a **Dismiss** action opening a small reason-required form (client-side validation mirrors the server's non-empty check, but the server-side `422` in AC-15 remains the actual enforcement — the client check is a UX nicety, not the security boundary). Edge case: a credential that has never been shared shows no badge at all (not an empty/greyed-out badge) — the badge's mere presence is itself the signal, matching this codebase's existing convention of omitting rather than graying out inapplicable UI (confirm this convention against the existing rotation-status badge's own empty-state handling and match it).

## Dev Notes

Do not invent an event-bus/pub-sub mechanism to avoid this direct call; this codebase's existing convention for same-transaction cross-module effects (e.g. Story 4-3's deactivation flow calling into `autoRevokeSharesForDeactivatedUser`, itself a `org` → `credential-shares` cross-module call already shipped in 17.1) is a direct function call inside the shared transaction, not an async/decoupled event.
- **`credential_shares.status` already includes `'superseded'` in its CHECK constraint** (confirmed by reading `packages/db/src/schema/credential-shares.ts`'s `statusCheck` — `IN ('active','viewed','revoked','expired','superseded')`, unchanged since migration 0059) and **`supersededAt` already exists as a column** — both were provisioned by 17.1 in anticipation of this story, per that story's own AC-6 note ("`superseded`... exists now... but is unused and unreachable from this story's routes"). This story's DB-layer work for supersession is therefore zero new columns on `credential_shares` itself — only the new `credential_share_nudge_dismissals` table (AC-10) needs a migration.
- **No dedicated audit event existed for expiry or supersession before this story** — confirmed by grep against `packages/shared/src/constants/audit-events.ts`: only `CREDENTIAL_SHARE_CREATED`/`_VIEWED`/`_REVOKED` exist today (17.1). This story adds the three events AC-5/AC-13/AC-15 specify. `AuditEvent`'s type is derived automatically from the object literal (`AuthAuditEventType = (typeof AuditEvent)[keyof typeof AuditEvent]`) — no second union to keep in sync.
- **`lazilyExpireShareIfDue`'s exact current body** (verified 2026-07-29): a bare `if (status !== 'active' || not-yet-expired) return share; else conditional UPDATE ... RETURNING`. Zero audit call today. ### Completion Notes List

**Prior elicitation (5 rounds applied during story creation, findings integrated directly into the ACs above rather than left as a separate section):**

1. **Security Audit Personas (Hacker / Defender / Auditor):** *Hacker* — a compromised or careless sharer could dismiss the rotation-recommended nudge to hide evidence of a share they don't want investigated, if dismissal were unauthenticated or unaudited. **Applied:** AC-15 requires `minimumRole: 'member'` (an authenticated, role-checked actor) and writes a dedicated `CREDENTIAL_SHARE_NUDGE_DISMISSED` audit entry recording who dismissed and the reason text verbatim — a dismissal is exactly as forensically visible as the share itself, closing the "quietly make the warning disappear" attack this persona surfaced. *Auditor* — without AC-13's supersession audit trail linking `rotationId` to each superseded share, an auditor reviewing why several shares changed state simultaneously would have no way to connect the dots without cross-referencing timestamps by hand. **Applied:** AC-13's payload explicitly includes `rotationId` on every supersession entry.

2. **Pre-mortem Analysis:** Scenario — the expiry sweep worker (AC-7) is built with a daily cadence (mirroring 5.6's stale-staged alert, the most recent precedent in the codebase) without questioning whether that cadence fits this epic's much shorter share-expiry windows (hours, not weeks) — six months post-launch, the Share History view is routinely showing "active" for shares that actually expired up to 24 hours earlier, quietly undermining trust in the whole feature this story exists to make trustworthy. **Applied:** AC-7/Dev Notes explicitly reasons through why an hourly (not daily) cadence is required here, as a judgment call the dev agent must make consciously rather than pattern-match to the nearest precedent without checking the underlying timescale.

3. **Failure Mode / Edge Case Analysis:** Scenario — a field-scoped rotation is promoted, and the supersession logic naively supersedes only shares with an exact `fieldKey` match, silently leaving whole-credential shares (which also exposed the now-stale field) marked `active` even though the value they showed is now partially wrong. **Applied:** AC-12's scoping rule explicitly requires whole-credential (`fieldKey IS NULL`) shares to be superseded whenever *any* targeted field is promoted, not just exact-field-match shares — this is the single most consequential correctness AC in the story's supersession scope and was not obvious from the sprint-change-proposal's one-sentence description of the Round 4 finding.

4. **Architecture Decision Records:** Recorded AC-8's lazy-plus-sweep decision explicitly (not left implicit) after considering and rejecting both lazy-only and sweep-only alternatives, matching the epic's original §1.2 design intent that 17.1 only partially implemented. Also recorded the cross-module dependency direction (`rotation` → `credential-shares`) as a conscious decision, confirming via direct import-graph inspection that it introduces no cycle, rather than assuming a same-transaction cross-module call is fine without checking.

5. **Challenge from Critical Perspective:** Initial draft treated "Share History UI/API" as needing a new unified listing endpoint, assuming 17.1/17.2 had built two separate paths for member vs. external shares. **Applied:** direct code inspection (AC-3) confirmed `listSharesForCredential` already returns both recipient types from one query — the AC was rewritten from "build a unified view" to "confirm the existing view is already unified, extend it with filtering/pagination/field-column only" — a real scope reduction caught only by reading the shipped code rather than trusting the task brief's framing of the gap.
